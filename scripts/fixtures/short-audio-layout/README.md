# Short audio layout experiment fixture

`failed-multitrack.webm` is the exact 59,365-byte generated source retained from
OpenLR Actions run [42381349345](https://github.com/stvlynn/OpenLR/actions/runs/42381349345),
Apple Silicon job 128429435884, artifact `audio-export-failures-macos-15`,
`trimmed-qk98Fu/multitrack.webm`. It was generated by OpenLR's
`tests/fixtures/multitrack-video.mjs` using Chrome 157.0.8103.38. It contains
generated color frames and tones, with no personal media or external assets.
The fixture and preparation code are project material under AGPL-3.0-only.
The recorded source revision is `df4900c`; this is retained failure evidence,
not a newly generated substitute.

The source imported successfully but its initial trim-player source preparation
failed with media error 3 before export. This does not establish a container
cause. The fixture has VP9 video and two Opus tracks, a 10,000 ns TimestampScale,
nine clusters, and an intentional 200 ms hole in the delayed stereo track.

From the repository root, prepare three controlled inputs with:

```sh
node scripts/prepare-short-audio-layout.mjs build/short-audio-layout
node --test scripts/prepare-short-audio-layout.test.mjs
```

The command copies `original-10000ns.webm` unchanged, then writes
`reticked-100000ns.webm` with the same nine cluster boundaries and
`regrouped-100000ns.webm` with three gap-preserving clusters at 0, 1.36, and 2 s.
Only 0 and 2 s begin with a video random access point (RAP). Regrouping reduces
non-RAP clusters; it does not eliminate them. The original 1.36 s boundary is
retained across the stereo gap to preserve the current application's packet
semantics. This is an unadopted container experiment, not a production repair.

The fixture-only structural writer follows [Matroska RFC 9559](https://www.rfc-editor.org/rfc/rfc9559.html)
and [EBML RFC 8794](https://www.rfc-editor.org/rfc/rfc8794.html). No outside
implementation was copied. It rejects non-exact reticking and out-of-range
block timestamps, preserves complete TrackEntry bytes and compressed packets,
reticks cluster/block/cue timestamps and explicit durations/references, and
rewrites and validates SeekHead/Cue positions. Original BlockGroups, priming,
discard padding, metadata, and the source's interleaved packet order remain
equivalent. Newly final SimpleBlocks receive the same explicit duration; video
delta blocks retain a reference to their preceding frame. The command neither
decodes nor encodes media. Its public MediaBunny readback checks decoder
configuration, every compressed packet, type, timestamp, duration, side data,
and metadata before writing `report.json` with `verified: true`. This reader
check is container validation, not a native playback result.

## Separate reader finding

The current MediaBunny Matroska reader replaces a block's explicit duration with
the distance to the next same-track block within its cluster. A RAP-only
regroup at 0/2 s therefore reports 220 ms for stereo packet 39 instead of its
original explicit 20 ms, even when that BlockDuration is retained. The public
remux API also did not preserve that duration under regrouping. Neither a reader
change nor a weakened duration assertion belongs in this experiment. Keeping
the existing gap boundary makes both candidates pass the original strict
packet-duration and gap checks. Investigating the reader behavior is separate
from establishing the native error's cause.

The preparer is deliberately limited to this finite, unlaced fixture shape;
it is not a general WebM remuxer. macOS playback and all existing independent
image/audio/original-byte assertions remain the comparison runner's job.

## Native comparison modes

The same runner and workflow support three controlled modes. After preparation,
pass a stock OpenLR executable, the prepared directory and a fresh report
directory. FFmpeg and ffprobe must be on PATH; an optional fourth positional
argument names their directory.

```sh
node scripts/native-audio-layout-comparison.mjs PATH_TO_OPENLR build/short-audio-layout build/audio-layout-trials --comparison=layout
node scripts/native-audio-layout-comparison.mjs PATH_TO_OPENLR build/short-audio-layout build/audio-read-trials --comparison=read-timing
node scripts/native-audio-layout-comparison.mjs PATH_TO_OPENLR build/short-audio-layout build/audio-recovery-trials --comparison=recovery
```

`layout` retains the three-arm schedule: original, reticked, regrouped,
regrouped, reticked, original, repeated four times, with eight fresh hosts per
arm. Every arm performs the added exact-original export/read before trim.
That read changes timing, so a null layout result cannot exclude the original
intermittent failure.

`read-timing` uses the exact original 59,365-byte input and one stock executable
for both arms. Its fixed order is original-workflow, added-read, added-read,
original-workflow, repeated six times: 24 fresh hosts, twelve per arm. The
diagnostic environment setting `OPENLR_AUDIO_ORIGINAL_BEFORE_TRIM=0` omits only
the added pre-trim original export/read, including the corresponding AAC-input
read. Setting it to `1` enables those two reads; the standalone smoke defaults
to enabled. The result parser requires exactly zero or two pre-trim receipts
according to the arm. Both arms retain every post-trim original-byte, image,
rotation, multitrack export, decoded audio and exact frame-count assertion.
There are no added delays or retries. A finite null timing result also cannot
establish elimination of an intermittent failure.

`recovery` runs the selected bounded initial playback recovery candidate against
the original workflow: one `original-workflow` arm, 24 fresh hosts, the exact
59,365-byte original and no added pre-trim read (zero required receipts).
Every strict post-trim original, image, PCM, frame-count and all-track export
assertion remains. The harness adds no delay or forced fault. Each trial's
`playbackLoadRetries` counts parsed `playback-load-retry` diagnostic records;
raw logs remain available. This count is observational and is not required for
a pass. A finite clean cohort without such an event does not demonstrate
recovery from a genuine failure or establish its root cause.

All modes use the shared scheduler and actual owned host/browser cleanup.
Semantic failures remain in the report; another host starts only after both
cleanup receipts and the smoke process's actual close. Cohort completion does
not mean every semantic assertion passed. The workflow's manual `comparison`
choice selects a mode; its self-path push trigger defaults to
`recovery`. The 24-trial budget remains 28 minutes for the comparison and
35 minutes for the job, with one preparation and one stock application build.

## Local verification

On Windows with Node 24.9.0, both focused tests passed, as did JavaScript syntax
and Prettier checks. Preparation produced files of 59,365 / 59,359 / 59,307 bytes
for original / reticked / regrouped. The original was directly compared with
the retained downloaded artifact bytes. An independent FFmpeg 8.1.2 comparison
found identical decoded bytes in all arms: 28 RGBA video frames, 130,560 mono
samples, and 85,120 stereo samples. FFprobe packet PTS/DTS and audio durations
also matched; video seek output matched at 1.36 and 2.1 s. FFprobe omits some
video SimpleBlock durations, so those fields are not an independent duration
oracle; the preparer's public-reader check requires every video and audio
duration to match. These checks do not establish macOS playback or the cause of
the retained error.

## Completed native observations

Apple Silicon run [42387471151](https://github.com/stvlynn/OpenLR/actions/runs/42387471151)
at `75ea466` completed all 24 strict trials, eight per input arm, including the
exact retained original. Each trial passed WebM, MP4 and 44.1 kHz AAC checks;
the logs retained 48 pre-trim original-byte receipts. All host cleanup was
confirmed, and all 24 distinct owned browser processes closed gracefully with
no forced cleanup. Artifact `13579334657` was audited under
`.workspace/audio-layout-75ea466/`.

A clean Windows build at the same revision used stock Go 1.27.3, FFmpeg 8.1.2
and Chrome 157.0.8103.38. The same 59,365-byte original passed every strict
check in 20.4 seconds, with confirmed host and graceful browser cleanup. The
log is `.workspace/audio-layout-windows-75ea466.log`. Neither result establishes
container causation or recovery from the native decode error. The original
also passed, and all these observations included the added pre-trim read;
the separate timing mode above tests that remaining design difference.

The subsequent `9004d23` read-timing cohort completed all 24 trials with 23 strict
passes: original-workflow passed 11/12 and added-read passed 12/12. Zero-based
trial 15, without the added read, reached metadata at 20 ms and suspend at
34 ms, then error 3 at 3,673 ms with ready state 0. No loaded data, seek or
export followed; the host remained responsive with a 9 ms UI-pump reply. All
24 host and browser cleanups were confirmed. Artifact `13581013252` is retained
under `.workspace/audio-read-timing-9004d23/`. This finite result establishes
neither a benefit from the added read nor the root cause of the failure. It
motivates testing the selected recovery candidate with the original workflow
and exact original input; it does not establish native recovery success.
