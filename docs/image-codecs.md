# Local image codecs

`web/formats.js` owns the export format contract used by the GUI, CLI schema, filename generation and codec adapter. Existing order is preserved: JPEG, PNG, Original, followed by TIFF, AVIF and JPEG XL. Originals return their existing bytes and filename. Re-encoded formats use `.jpg`, `.png`, `.tif`, `.avif` or `.jxl` and the matching MIME type. Original processing supplies the rendered canvas; Linear supplies its edited float result after crop and optional watermark/resize. The [output color adapter](export-color.md) converts samples to the requested space and embeds matching profiles for supported formats.

## Format behavior

| Format | Import | Export | Quality |
| --- | --- | --- | --- |
| JPEG / PNG | Native browser image codec for Original; PNG Linear uses shared numeric reconstruction before color interpretation | Native encoding for sRGB; converted samples with ICC for other named spaces (explicit PNG encoder, native JPEG compression) | JPEG 0–1; PNG has no quality control |
| TIFF | Shared corrected UTIF, first image and orientation; Linear retains supported integer samples and RGB matrix/TRC input profiles | Dynamic uncompressed RGBA TIFF with unassociated alpha and ICC; 8-bit Original or 16-bit Linear | Not exposed |
| AVIF | Rebuilt libavif decoder; Linear requests integer RGBA16 from 8/10/12-bit sources before supported ICC/SDR conversion | Rebuilt libavif encoder, 8-bit samples with target ICC | 0–1; exactly 1 selects the codec's true lossless mode |
| JPEG XL | Rebuilt shared libjxl/skcms decoder, native FLOAT for Linear and legacy RGBA8 for Original | Rebuilt public libjxl encoder, 8-bit samples with target ICC | 0–1; exactly 1 selects true lossless mode |
| Camera RAW/DNG | LibRaw adapter | Original bytes or a rendered raster format | See [RAW decoding](raw-decoding.md) |

The shared input accept list includes TIFF/AVIF/JXL extensions, and the CLI gives imported files the corresponding MIME type. `decodePhoto` owns display decoding and `decodePhotoFrame` owns Linear source decoding for import, original reload and export source loading; both use the shared codec kernels. Filenames do not get relabeled without actual encoding. TIFF's unassociated-alpha tag matches `ImageData`; imported associated-alpha samples are unpremultiplied before display or input color conversion. TIFF floating point, unsupported layouts and sensor DNG disguised as TIFF are rejected visibly rather than silently rendered as zeroes. A `.dng` source goes through LibRaw.

Original processing exports use the 8-bit canvas pipeline. Linear processing converts its Float32 result directly into 16-bit TIFF or target-space 8-bit samples for the other rendered formats. Rendered exports do not preserve arbitrary original EXIF/ICC/animation/multiple-page structure or create a sensor RAW master. Named target profiles are generated independently. TIFF exports normally use classic TIFF, with BigTIFF layout for offsets beyond 32 bits; multi-gigabyte allocation/interoperability is untested and the importer accepts classic TIFF only. TIFF import takes the first image rather than creating a page sequence. Generic unprofiled CMYK conversion is not an ICC-managed print workflow; incompatible embedded color-profile layouts are rejected. AVIF/JXL use rebuilt bindings with the pinned codec revisions and support all five named output spaces. Original export remains the path for preserving original compressed bytes and metadata.

The [linear input contract](linear-working-frames.md) owns exact PNG/TIFF layouts, native AVIF/JPEG XL depth, alpha/orientation, CICP assumptions and precision provenance. [Color handling](export-color.md#input-color-and-re-import) owns the supported ICC matrix/TRC subset. Structurally valid unsupported RGB profiles/CICP can take explicit `rgba8-display` compatibility, while malformed input fails visibly. PQ/HLG working conversion and general CMYK color management remain outside that native-sample path. JPEG XL reuses bundled skcms for its supported profiles, including in-range LUTs; unbounded sampled-profile input takes explicit compatibility. A 16-bit transport buffer does not imply 16-bit source precision.

## Worker lifecycle and native compatibility

Rendered JPEG/PNG/TIFF/AVIF/JPEG XL can explicitly include [selected copyright and photo fields](export-metadata.md). The shared EXIF/XMP policy rebuilds output dimensions/orientation and retains the selected target ICC; it does not copy arbitrary source blocks. None remains the existing default. AVIF/JXL encoder bindings use their pinned libraries' metadata APIs and retain the original no-metadata path.

`web/raw-kernel.js` and `web/codec-kernel.js` own the implementations. The Worker files are thin message/transfer adapters. `web/image-worker.js` serializes heavy codec jobs and terminates each normal Worker after success or failure, releasing its WASM heap. An explicit startup handshake happens **before** transferring an encoder's pixel buffer.

Some native custom-scheme hosts cannot construct/load module Workers. If construction throws, or the Worker module fails before the handshake, the runner terminates it and dynamically imports the exact same kernel on the main thread. It does not invent a second decoder, retry processed corrupt inputs, or convert runtime decode failures into success. Normal browser hosts keep the isolated path. `main.go` registers `.js` / `.mjs` as JavaScript and `.wasm` as WebAssembly independent of OS file associations.

Fallback creates a console diagnostic and an entry in `state.codecDiagnostics`, also accessible through `getImageWorkerDiagnostics()`. Records include the Worker module name, startup phase, fallback route and error message; photo filenames/contents are not recorded. The list retains 20 entries. Main-thread fallback can block the UI and retain a reusable WASM high-water heap despite per-photo disposal; the two-minute Worker cancellation boundary cannot interrupt synchronous main-thread WASM execution. This compatibility path is a tested fallback, not a claim of identical memory isolation.

## Checks

Run `node --test tests/codecs.test.js tests/worker-fallback.test.js tests/raw.test.js` with installed Chrome and a reachable local HTTP server. On Windows/Chrome, generated 32×24 RGBA gradients round-trip losslessly through TIFF/AVIF/JXL with measured maximum channel difference **0**. The current writer emits classic TIFF `II 2A 00` (the previous writer emitted `MM 00 2A`), AVIF `ftyp`/`avif`, and JXL `FF 0A` signatures. Tests also verify lossy quality, corrupt-input rejection, GUI import/export and quality visibility, exact extensions, TIFF Deflate/orientation/associated alpha, and both normal and cross-origin-isolated threaded encoders. Forced Worker constructor failures and real 404 Worker-module loads still decode DNG and round-trip all three raster formats through shared kernels; processed corrupt RAW does not trigger compatibility fallback. Physical-camera files, arbitrary TIFF encodings, animation, other operating systems/WebViews and huge images need further coverage.

`node --test tests/tiff-layout.test.js tests/float-tiff.test.js` checks 1,056 generated stripped/tiled 8/16-bit layouts with both endian modes, predictors 1/2, RGB/grayscale and alpha, and uncompressed/LZW/Deflate/PackBits storage. It also bounds missing-EOI/truncated LZW failures in an isolated Worker and verifies deterministic vendor patch application. `node scripts/experiments/tiff-precision.mjs` records every numerical case under ignored `.workspace/tiff-precision/`. See [the TIFF precision investigation](../research/high-depth-tiff.md) for original failures, targeted repair and evidence limits. These synthetic layouts do not prove arbitrary TIFF interoperability.

PNG Linear input uses independently implemented sample reconstruction with existing pako. `web/png-container.js` owns chunk/CRC primitives shared with the existing PNG output writer, whose byte layout is unchanged. `web/png-color.js` owns PNG-specific characterization precedence and delegates numerical transforms to the shared color owners. The same codec Worker and main-thread fallback serve both TIFF/AVIF and PNG working input. Original PNG display retains the native decoder and color management; `web/png-display.js` applies EXIF orientation explicitly so Chromium and WebKit agree. Only its temporary decode Blob omits eXIf, and the existing pixel mapping applies direction once. Other chunks and original-file bytes remain intact. Linear compatibility decoding uses the same display adapter. Display decoding leaves CRC policy to the host; numeric reconstruction and output retain their existing strict checks. See [PNG contracts](linear-working-frames.md) and [reconstruction evidence](../research/high-depth-png.md). Animation editing, arbitrary resource consumption and unsupported HDR characterization are not established by first-frame decoding.

Older catalog PNG previews are refreshed when visible through the existing RAW preview queue. The cache write persists the decoded source dimensions, rendered thumbnail and `pngPreviewVersion` together, without creating edit history; replaced photo rows invalidate stale work. New imports and generated results stamp their current preview immediately. Local-folder previews already decode from their sources on visibility. Existing edit coordinates remain unchanged: an old recipe made against an incorrectly oriented WebKit source can therefore change appearance when its source orientation is corrected. `tests/png-preview.test.js` verifies persisted old-cache repair, queued row replacement, missing IntersectionObserver and editing before lazy refresh, with byte-identical originals.


## Optional worker cancellation

`runImageWorker(url, message, transfers, fallback, { signal })` accepts an optional AbortSignal. Existing callers without a signal retain their serialized behavior. Aborting rejects with `name: AbortError` and `code: ABORTED`. A queued request releases its payload references without constructing a worker; a request canceled before the handshake leaves its transfer buffers attached. After handoff, cancellation terminates that worker and its owned buffers are no longer reusable. Callers must retain their original source separately.

Cancellation never invokes startup fallback. If a startup fallback has already begun asynchronously, the caller can stop waiting immediately but its queue slot remains occupied until the fallback settles. This prevents the next image heap from overlapping unfinished fallback work; a late bitmap result is closed. Synchronous fallback cannot be interrupted while it occupies the main thread. Listener cleanup and queue recovery apply after success, failure and cancellation.

The thin `dehaze-worker.js` imports the existing exact analyzer. `analyzeDehazeOwned` transfers an owned corrected frame after the handshake and returns that frame with the transmission map, using transfer lists in both directions. Startup failure uses the same analyzer before ownership transfer; processing failures are not retried. This adapter alone does **not** make the application renderer asynchronous: source/revision-aware preparation and UI/export callers must still be wired as described in [the background proposal](../research/dehaze-background.md).

`node --test tests/worker-cancel.test.js tests/worker-fallback.test.js tests/dehaze-worker.test.js` exercises real browser workers, queue recovery, pre-handshake/active/queued cancellation, asynchronous fallback serialization, exact map/pixel equivalence, original-buffer preservation and browser event-loop heartbeat. Native host integration remains separate acceptance.

The optional synchronous `prepareMessage(input)` returns `{message, transfers}` after queue admission and before worker construction. Use it when a task needs a large owned copy of an immutable shared input: pending tasks retain references, not preallocated copies. Queued cancellation never calls it. Preparation failure rejects directly and releases payload references; it is not a worker startup failure and must not invoke fallback. Once prepared, startup fallback receives that same owned message before any transfer. Existing eager callers keep their behavior. This bounds preparation to the active queue slot, not total retained source memory; callers still own source lifetime and cancellation. The Chrome test above checks allocation counts while an asynchronous fallback occupies the queue, canceled queued input, preserved original bytes, startup fallback and recovery after allocation failure.
