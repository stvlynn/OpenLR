# Rendered metadata evidence and experiments

The [installed Lightroom 9.4 runtime observation](lightroom.md#登录后的-windows-运行观察) records the export preview's all-metadata/copyright-only controls. The preview was cancelled; no Adobe output file was produced or inspected. The [official cloud-desktop export guide](https://helpx.adobe.com/lightroom/desktop/save-share-and-export/save-share-photos.html) also describes metadata options. These support the workflow investigation, not a claim about Adobe's precise tags or algorithms. OpenLR's bounded field policy is an independent product decision.

Primary source inspection used the pinned [libavif API](https://github.com/AOMediaCodec/libavif/blob/d1c26facaf5a8a97919ceee06814d05d10e25622/include/avif/avif.h), [libjxl encoder API](https://github.com/libjxl/libjxl/blob/9f544641ec83f6abd9da598bdd08178ee8a003e0/lib/include/jxl/encode.h) and [actual box reader/writer](https://github.com/libjxl/libjxl/blob/9f544641ec83f6abd9da598bdd08178ee8a003e0/tools/box/box.cc). The fixed libjxl header comment uses `XML `, while the actual container implementation uses lowercase `xml `; output follows the actual standard box type. Libavif's EXIF setter can derive image transforms from Orientation, so new EXIF is normalized to 1 before it reaches the library.

The [IPTC mapping guide](https://www.iptc.org/std/photometadata/documentation/mappingguidelines/) distinguishes Copyright/rights and creator and documents EXIF/XMP mappings. [PNG 3](https://www.w3.org/TR/png-3/) defines eXIf and UTF-8 iTXt. [LibTIFF's BigTIFF specification](https://libtiff.gitlab.io/libtiff/specification/bigtiff.html) defines 64-bit directory offsets and IFD8. Sources were consulted for interoperability; no proprietary resource payload or upstream photo was copied.

## Generated input

`node research/export-metadata-fixture.mjs` creates `.workspace/export-metadata/source.png` with original generated 32×24 samples and an ExifTool argument file. Apply the argument file using the fixed official ExifTool source (13.60), then copy the resulting 1,931-byte PNG to `tests/fixtures/export-metadata.png`. The fixture contains fictitious camera/author fields, an explicit `+08:00` capture offset and subseconds, Orientation 6, distinct ASCII EXIF and Unicode XMP rights, and deliberately excluded GPS, keyword and Camera Raw adjustment fields. The Unicode text includes XML reserved characters, emoji and a combining mark. ExifTool writes PNG text mirrors as well as EXIF/XMP; selected-field input must not accidentally copy those ancillary source text chunks into output.

ExifTool's [fixed source and license](https://github.com/exiftool/exiftool/tree/980409314fddbd83d9092b5c160fafab7f67fd52) were checked: it uses Perl's Artistic/GPL terms, not MIT. It is kept under ignored `.tools/` solely as an independent oracle. No runtime dependency or copied ExifTool source is shipped.

## File and pixel experiments

Serializer comparison used five actual generated PNGs and ExifTool 13.60. The existing shared IFD writer plus Unicode XMP and a scratch piexifjs ASCII-filtered variant plus the same XMP both recovered the ten selected fields, offset/subseconds and Unicode text. Unmodified piexifjs 1.0.6 threw on OffsetTimeOriginal tag 36881; the experiment required adding that tag definition locally. Directly putting Unicode into its legacy ASCII EXIF strings produced independently observed garbled rights/creator text. The selected implementation therefore reuses OpenLR's existing typed TIFF layout and places Unicode in XMP. No piexifjs code or dependency was imported; the decision is based on field correctness and shared responsibility, not a claim that a slightly smaller sample is universally faster.

Context7 `/hmatoba/piexifjs` and `/exiftool/exiftool` supplied API discovery, followed by inspection of the fixed sources. The candidate [piexifjs revision](https://github.com/hMatoba/piexifjs/tree/2180d60b8cdf638e236e0a6703b7c378bb4f5785) declares package version 1.0.6 although its source version string is 1.0.4; its [MIT license](https://github.com/hMatoba/piexifjs/blob/2180d60b8cdf638e236e0a6703b7c378bb4f5785/LICENSE.txt) was checked before the scratch experiment. Its JPEG insertion API was not assumed to support every container. The retained production tests reproduce the selected writer's independent EXIF/XMP readback, while the candidate remains outside the runtime and dependency lock.

The real-browser application exports 30 files: two processing versions × five formats × three policies, after source orientation, crop, turn, long-edge resize and Display P3 conversion. Independent ExifTool checks rights, creator, camera fields, output dimensions/orientation, and removal of GPS/private edits. Actual decoding compares the pixels across policies. JPEG XL's original codestream ICC is read by libjxl because this ExifTool version does not expose it. GUI download, previous settings, restart and exact original-byte export are checked in the same workflow.

Separate real WASM experiments exercised AVIF scalar/threaded and JPEG XL scalar/threaded/SIMD with EXIF-only, XMP-only and combined payloads, plus sRGB/P3 and lossy/lossless cases. ExifTool read 25 actual files without warning/error. Pixels and ICC were unchanged by metadata, and metadata-disabled output matched the previous encoders byte-for-byte in the compared cases; JPEG XL's boxed image codestream matched its bare output. These are generated-sample measurements, not universal codec or viewer equivalence claims.

JPEG/PNG/TIFF tests independently read EXIF, inspect Unicode XMP with a native XML parser, preserve compressed JPEG/PNG payloads, and verify TIFF low bits across multiple strips. Exact APP1 payload limits are exercised. BigTIFF offset handling was extended in the shared writer, but no multi-gigabyte allocation or external BigTIFF interoperability is claimed. Full local/native/platform outcomes belong to [acceptance](../docs/acceptance.md).
