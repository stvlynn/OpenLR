# Mask and histogram consistency

The 2026-11-06 investigation uses generated images and the current OpenLR application. These are OpenLR observations, not claims about Lightroom's algorithms. The initial browser probe and finite native verification plan are retained in ignored `.workspace/image-native-browser-probe.mjs` and `.workspace/image-native-plan.md`.

## Mask coverage and removal

On a 96×64 gray PNG with two small red patches, a manual red-eye correction changed the left sample to `[26,29,22]`. A red color-range adjustment correctly excluded that corrected sample in the rendered photo. Original processing's `mask-preview` nevertheless reported full coverage there; Linear processing reported zero. Both processing versions' range-based removal selected both red patches from the uncorrected bytes. Separately, square aspect exported a 64×64 photo but a 96×64 mask preview.

The shared source correction owner now supplies fill → red-eye → repairs to coverage, matching the renderer's pre-mask reference. Mask preview forwards aspect to the existing geometry renderer. Removal uses this reference only for range selection; its baked patch still uses the existing pre-eye/pre-repair byte stage. Baking the corrected reference directly was rejected because later red-eye and repairs would then be applied twice. Existing fill placement and byte precision are preserved; subsequent repairs may still composite over a fill. Linear reference buffers are owned copies before worker transfer, so cached source samples remain attached and retain their float distinctions.

A subsequent actual Chrome comparison against an isolated `git archive b06a522 web` confirms the remaining opaque-clone boundary. A radial/color intersection selects 25 pixels in both mask previews. Baseline removal rejects it because the underlying uncorrected destination is outside the color range; the current reference permits a 5×5 fill and consumes the mask. The later opaque clone covers that fill, so both before/after exports remain identical. A geometric radial selecting those same 25 pixels already saved an invisible fill in both versions. All four cases retained the clone and original bytes. This is a confirmed limitation of the existing fill-before-repair composition, newly reachable through consistent range selection, not proof of useful removal over an opaque repair. The ignored `.workspace/clone-removal-repro.mjs`, log and PNGs retain the comparison. Defining useful removal across repair layers remains follow-up; this increment does not silently reorder stored patches or add a refusal for overlap.

`tests/removal.test.js` verifies both versions, both solvers, cropped/flipped/rotated coverage, independent output pixels, unchanged exterior, undo and original bytes. `tests/float-mask-preview.test.js` also tests two different float samples with the same display byte: only the intended sample is selected and the source survives the worker transfer. The focused Windows Chrome/unit run passed 27/27. The corresponding actual CLI checks live in `scripts/native-mask-smoke.mjs`; executed platform results belong in [acceptance](../docs/acceptance.md).

## Displayed histogram

The original Compare Pair panel used its first canvas on opening and its edited canvas on repaint. The same generated gray image and Exposure +1 therefore showed peak 96 on opening and 133 after zoom. The committed CLI histogram remained 133. Clipping warnings also mutate the visible canvas, making a later canvas read differ from a pre-warning repaint.

The application retains the published preview's histogram, tied to its photo and mounted canvas. In Pair this is the edited pane; in original comparison or a transient adjustment it follows the displayed preview. It computes bins before painting clipping warnings, otherwise only when requested. This reuses the existing capped histogram sampler and avoids reading a canvas for an unopened panel with warnings disabled. `histogram` keeps its committed-image default; optional `source:display` exposes the same bins as the panel, with an owned response and a visible error outside Detail. No edit or catalog state is introduced.

`tests/histogram-workflow.test.js` checks exact independently calculated arrays and the actual graph through trusted panel activation, repaint, comparison, clipping, an uncommitted slider preview, response mutation and Grid. The test plus existing panel and point-color checks passed 4/4 in Windows Chrome. Native navigation checks compare returned bins to decoded exported pixels; they do not substitute for the browser's actual graph and draft observations.
