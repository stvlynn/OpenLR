# Shared range-color sampling research

Date: 2026-11-05. This concerns OpenLR's existing source-color contract and GUI/CLI consistency, not a reconstruction of Adobe's unpublished color metric.

## Evidence boundaries

The [Lightroom evidence index](lightroom.md) records REA resources R1/R3 and local resource observations L1/L2. Those establish masking/organization entry points. Earlier Windows UI observation opened masking controls, but did not measure the source buffer, pixel neighborhood, color conversion or coordinate algorithm used by Adobe's range sampler. None of the conclusions below imply that those Adobe internals were recovered. No Adobe code, photograph or asset is used in the experiment.

OpenLR's [range-mask contract](../docs/range-depth-tools.md) already says that range picking samples an original decoded pixel after reversing the displayed geometry. The existing `sample-color` CLI contract instead samples the edited preview. These are intentionally different values; making the latter silently return source pixels would break its established meaning.

The prior actual Chrome audit at `67fedc9` used a generated 40×40 PNG filled with `#406080`, with Exposure +1. Activating **Sample range color** during crop left `cropping=true`, no local overlay and unchanged draft color `#808080` after a real image click. After leaving crop, the same pointer action sampled `#406080`. `sample-color` correctly returned edited `#5a85b0`. Evidence and reproduction are retained in ignored `.workspace/gui-command-audit.json` and `.workspace/gui-command-audit.mjs`. This is observed OpenLR behavior, not a Lightroom runtime comparison.

## Primary API and source checks

Context7 `/mdn/content` was resolved and queried for Canvas source rectangles and pixel readback. Its results were checked against primary MDN pages and their [drawImage source](https://github.com/mdn/content/blob/main/files/en-us/web/api/canvasrenderingcontext2d/drawimage/index.md) and [getImageData source](https://github.com/mdn/content/blob/main/files/en-us/web/api/canvasrenderingcontext2d/getimagedata/index.md).

- [`drawImage`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage) accepts an explicit source rectangle and a destination rectangle, including `ImageBitmap` and video sources. A 1×1 integer source rectangle copied into a 1×1 canvas does not require another full-size sampling canvas.
- [`getImageData`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getImageData) reads canvas pixels independently of the context transform. Geometry therefore must be inverted by the existing OpenLR mapping before source sampling; applying a canvas transform and expecting readback coordinates to follow it is incorrect. Ordinary readback supplies byte RGBA values; optional wider pixel formats do not turn the existing hex color control into a high-depth sample API.

Source inspection of `web/edit-source.js` shows that Original processing uses the normal decoded display source. Linear processing binds a high-precision working frame to an explicitly converted 8-bit sRGB display surface. The range picker's existing hex reference comes from that surface. It must not be advertised as an unclipped float, RAW mosaic or sensor sample. Mask evaluation has its own documented pre-mask buffer, including repairs; source sampling retains its existing pre-edit meaning.

## Executed sampling ablation

Windows, Node 24.9, actual Chrome 155. A generated 64×32 PNG contains two flat patches: left `#406080`, right `#90a020`. Both processing versions were decoded through `decodeEditSource`. Three positions (`x=.25`, `.75`, `1`; `y=.5`) compared (a) a complete source canvas, (b) a 1×1 source rectangle, and (c) the existing edited preview after Exposure +1. At `x=1`, the integer source index is clamped to the last pixel, matching the established picker convention.

| Source patch | Versions | Full source canvas | 1×1 source rectangle | Edited preview |
| --- | --- | --- | --- | --- |
| Left | 1 and 2 | `#406080` | `#406080` | `#5a85b0` |
| Right and right edge | 1 and 2 | `#90a020` | `#90a020` | `#c5da2f` |

All six source comparisons were exact. All six edited values differed from the corresponding source value. Results are in ignored `.workspace/range-sample-ablation.json`; the executed script is `.workspace/range-sample-ablation.mjs`. This proves the distinction on these generated byte-color patches and confirms the one-pixel implementation against a full source canvas. It does not establish every codec/profile, transparent pixel, HDR source or browser's readback behavior.

Reproduction core, executed in a browser page served by `tests/browser-server.mjs`:

```js
const { decodeEditSource } = await import('./edit-source.js')
const { render } = await import('./render.js')
const { sampleColor } = await import('./point-color.js')
const input = document.createElement('canvas')
input.width = 64; input.height = 32
const context = input.getContext('2d')
context.fillStyle = '#406080'; context.fillRect(0, 0, 32, 32)
context.fillStyle = '#90a020'; context.fillRect(32, 0, 32, 32)
const blob = await new Promise(resolve => input.toBlob(resolve))
const file = new File([blob], 'generated.png', { type: 'image/png' })
for (const version of [1, 2]) {
  const source = await decodeEditSource(file, { processVersion: version })
  const whole = document.createElement('canvas')
  whole.width = source.width; whole.height = source.height
  whole.getContext('2d').drawImage(source, 0, 0)
  const edited = render(source, { processVersion: version, Exposure: 1 }, 1280)
  for (const x of [.25, .75, 1]) {
    const one = document.createElement('canvas')
    one.width = one.height = 1
    one.getContext('2d').drawImage(source,
      Math.min(source.width - 1, Math.floor(x * source.width)), 16,
      1, 1, 0, 0, 1, 1)
    const values = [sampleColor(whole, x, .5), sampleColor(one, 0, 0), sampleColor(edited, x, .5)]
    if (values[0] !== values[1] || values[1] === values[2]) throw Error(JSON.stringify(values))
    console.log(version, x, values)
  }
  source.close?.()
}
```

## Independent implementation decision

Keep edited `sample-color` unchanged. Introduce a discoverable source-range sampling command and route GUI activation through the existing local-tool dispatcher. Use the existing source decoder, source-coordinate mapping and color extraction owner, rather than a second decoding or geometry pipeline. Pointer commands carry the intended photo and mask/component target so queued work cannot silently apply to a different selection. Sampling a draft changes session state; refining an existing range uses the ordinary mask/component update and undo/persistence path.

Changing the old edited default is rejected by the measured semantic difference. Leaving activation in a private GUI closure is rejected by the observed crop failure and lack of CLI observability. Merely adding a source readback command without routing GUI activation would leave that failure intact. A whole-source sampling canvas produced the same values in the experiment, so its additional full-frame allocation is unnecessary for a single point.

Acceptance must separately cover actual crop/compare/pair transitions, original-coordinate sampling after rotation/flip/crop/optics, both processing versions, selected composite components, stale-photo/target handling, draft versus saved-mask effects, unchanged originals, and native CLI data plus actual screenshots. The ablation alone does not prove those workflows; final outcomes belong in the corresponding tests and [acceptance record](../docs/acceptance.md).
