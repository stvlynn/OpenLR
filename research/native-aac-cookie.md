# AAC configuration at the AudioToolbox boundary

The renderer needs two representations of the same configuration. AAC container tracks carry `AudioSpecificConfig` as decoder description bytes. AudioToolbox consumes and emits an MPEG-4 elementary stream descriptor around those bytes. The decoder needs the raw `ES_Descriptor` payload used in `esds`, starting at tag `0x03`. Apple documents this cookie representation, and WebKit's Cocoa AAC decoder wraps the WebCodecs description before asking AudioToolbox for stream format information. Chromium's macOS AAC encoder performs the inverse operation by reading the returned descriptor and extracting `DecoderSpecificInfo`. [Apple CAF specification](https://developer.apple.com/library/archive/documentation/MusicAudio/Reference/CAFSpec/CAF_spec/CAF_spec.html) · [WebCodecs AAC registration](https://www.w3.org/TR/webcodecs-aac-codec-registration/#audiodecoderconfig-description) · [WebKit decoder change](https://github.com/WebKit/WebKit/commit/9c36ab4353246d9f8155ff1b7ac05e688be5a5aa) · [Chromium AudioToolbox encoder](https://chromium.googlesource.com/chromium/src/+/refs/tags/148.0.7769.0/media/filters/mac/audio_toolbox_audio_encoder.cc)

## Conversion contract

- Encoding uses `aacDescriptionFromCookie(cookie, format)` with the negotiated native sample rate and channel count. The parser reads lengths of one through four bytes within each parent descriptor, skips optional ES fields, and requires unique MPEG-4 audio `DecoderConfigDescriptor` and nested `DecoderSpecificInfo` descriptors. It returns an owned copy of the exact description.
- Decoding uses `aacDecoderCookie(description, format)` with the demuxer's declared sample rate and channel count. The wrapper emits a raw ES descriptor with an MPEG-4 audio stream and the exact input bytes as `DecoderSpecificInfo`. WebKit's Cocoa helper uses the same compact structure without an `SLConfigDescriptor`. The wrapper leaves buffer and bitrate fields unspecified because the input description does not provide them. AudioToolbox still negotiates and verifies the actual format. [WebKit descriptor writer](https://github.com/WebKit/WebKit/blob/9c36ab4353246d9f8155ff1b7ac05e688be5a5aa/Source/WebCore/platform/audio/cocoa/AudioUtilitiesCocoa.cpp#L46-L128)
- The native path is scoped to independent 1024-frame AAC-LC, mono or stereo, with the sample rate and channel count matching the declared or negotiated format. Both indexed and explicit sample rates can be checked against the supplied rate. The helper accepts the AAC-LC sync extension when it explicitly signals that SBR is absent and preserves its bytes. Channel layouts requiring a program config element, HE-AAC, a dependent core coder, and 960-frame configuration fail validation. Codec timing, priming and padding are handled outside this conversion.

## Verification

Retained arm64 and x86-64 macOS audio probes each report a 39-byte encoder cookie and successful native decoding at 48 kHz mono and stereo and at 44.1 kHz stereo. For the 9,601-frame fixture, each result reported 12,288 coded frames, 2,112 leading frames and 575 trailing frames. The probe passed the original cookie into the native decoder. The earlier Chrome comparison supplied a fixture-derived two-byte AAC-LC configuration.

The arm64 probe subsequently recorded the actual AAC cookies. Each contains four-byte descriptor lengths, an `SLConfigDescriptor`, and downstream AudioStream flags `0x14`. ISO/IEC 14496-1 defines the low bit as reserved and specifies `1` for writers. The reader accepts either reserved-bit value while checking the six-bit AudioStream type and the downstream direction. The decoder wrapper continues to write `0x15`. The captured cookies extract `1188` for 48 kHz mono, `1190` for 48 kHz stereo, and `1210` for 44.1 kHz stereo.
