# Video export audio timing and codec adapters

The video-container export owns one `Input`, one `Output`, a trim range and the edited frame callback. Sample-accurate mono and stereo AAC-LC and Opus tracks use an explicit packet source on that same timeline. The export selects WebCodecs and the macOS AudioToolbox bridge by the actual codec configuration. Ordinary-only exports can continue using the MediaBunny conversion. The preview element and its clock never supply export samples or timestamps. [Video export](../web/video.js) · [Desktop CLI contract](../docs/agent-cli.md)

## Per-export ownership

1. Enumerate tracks with their decoder configuration, rate, channel count, language, disposition and pairability before starting output. Choose decode and encode capability separately. Opus uses the bundled decoder and AAC-LC uses a raw decoder that accounts for all coded samples. The precise output path supports Opus at 48 kHz and AAC-LC at 44.1 and 48 kHz, each in mono and stereo. Additional tracks in a mixed export require an exact encoder configuration to preserve their sample rate and channels. A missing exact capability produces a track-specific error.
2. Use `Conversion.init({ composable: true, copy: false, trim, … })` for the edited video and retained audio tracks in a precise export. `copy: false` anchors the conversion timestamp offset to the requested trim start. Set `audio(track)` to discard only tracks that have a matching explicit `EncodedAudioPacketSource`, and reconcile `utilizedTracks` plus planned replacements with every input track before starting the output. Preserve input name, language, disposition, metadata tags and track groups when constructing the replacement. A replacement track with no audible overlap fails before output starts.
3. Bind bounded native codec streams to one export and the originating native window. The bridge opens a converter with codec, direction, exact sample rate and channel count, verified codec description and optional frames per packet. It returns an opaque stream ID and negotiated configuration. Each process call carries at most 64 KiB of packed coded data or interleaved little-endian Float32 PCM. Decode input includes packet offsets, sizes and coded frame counts. A reply returns owned bytes, packet descriptions for encoded output, produced frames, consumed frames and terminal or needs-input flags. Submit the next chunk only after `NeedInput`. Finalize by passing EOF and pulling until `Done`. Read encoder prime and output description before closing. A stream from another native window or an ended export cannot be reused.
4. Drive the audio tracks and composable conversion in shared timestamp windows using `conversion.execute({ until })`, so one producer cannot queue an entire track while another starts later. Hold the first packet until the encoder's priming and description are known. Retain the tail until total coded and audible counts establish its discard. WebM's final block can represent only the padding in that block. If whole trailing packets contain only padding, omit them once the coded boundary is known. On failure or abort, close each stream, cancel unfinished conversion and output work, and dispose the shared input while retaining the primary error. Save the export only after output finalization and track reconciliation. Keep user data out of diagnostics. [Native stream protocol](../internal/nativeaudio/stream.go) · [MediaBunny composable conversion](https://github.com/Vanilagy/mediabunny/blob/v1.65.1/src/conversion.ts)

## Sample clock and prerequisites

`web/audio-timing.js` intersects requested and intrinsic presentation ranges on an integer sample clock. It rounds each shared boundary once, so adjacent trims meet on the same sample. A delayed track keeps its positive offset from trim zero. The encoded first packet starts at audible start minus the measured encoder prime. Later packet times advance by cumulative coded samples. The final discard is the completed coded count minus leading prime and submitted audible frames. The MP4 movie timescale is the least common multiple of the chosen sample rates and MediaBunny's existing 57,600 ticks per second, bounded by the unsigned 32-bit container field. For Opus WebM the proven explicit mode uses 10 µs timestamp ticks. [Timing patch and independent verification](audio-container-timing.md)

The decode adapter needs the coded frame position represented by the first returned PCM frame. `ConsumedFrames` measures input consumption and `Frames` measures raw output. Together they do not say whether a short output is buffering, a leading omission, or tail behavior. Both tested macOS architectures omitted the first 120 samples of the tested CELT-only Opus sequence, even with different cookies. The selected libopus adapter returns the TOC-defined frame count and has independent mixed-mode and preroll evidence in [the decoder record](native-audio-origin.md). [Observed AudioToolbox behavior](native-video.md) · [Opus packet structure](https://www.rfc-editor.org/rfc/rfc6716.html#section-3)

For an interior decode, use the previous key packet at least the track's declared preroll before the requested start and retain its actual coded timestamp. Apply Opus pre-skip as a stream-origin presentation bound. When starting later, it does not become new codec priming. Apply MP4's finite intrinsic edit and signed WebM discard on the original coded timeline, once. Preserve actual gaps. Distinguish container tick quantization from genuine discontinuities before advancing the integer PCM clock. The source patch exposes a laced block's padding on the expanded boundary packet. If the discard extends across several lace packets, the caller must resolve its block span before emitting affected samples or fail visibly. A large decode counter or a rounded packet timestamp is insufficient to reconstruct omitted source audio.

The native converter currently returns an opaque AudioToolbox cookie. Verify its AAC `DecoderSpecificInfo` before constructing a muxer `AudioSpecificConfig`, and exercise the corresponding decoder cookie path on both macOS architectures. The earlier Chrome packet probe built an AAC-LC configuration from its known fixture rates and channel count. It does not establish support for every incoming AAC profile or channel layout. For Opus output, build and verify an `OpusHead` consistent with the negotiated rate, channel mapping and measured priming before using it as the muxer's decoder description. The Go stream package currently accepts one or two channels. A fallback unable to preserve a source layout must fail without falling through to MediaBunny's default downmix. [AudioToolbox packet evidence](native-video.md) · [Opus identification header](https://www.rfc-editor.org/rfc/rfc7845.html#section-5.1)

## Implemented boundary and current verification

`web/native-audio.js` owns the bounded renderer transport, `web/browser-audio.js` owns per-export WebCodecs streams, `web/audio-track.js` owns the source sample clock and presentation intersection, and `web/audio-export.js` owns the replacement packet sources and composable conversion. Browser AAC feeds 2,048 silent warmup samples before the selected audio. It measures the resulting priming using two distinct pulses at the actual rate and channel count. Windows Chrome measured 2,048 priming samples after warmup. The same codec without warmup measured zero net delay and suppressed early signal. Browser Opus uses the encoder's reported header for priming and the packet TOC for coded duration. Both encoders share the packet timing and tail discard path with AudioToolbox. [WebCodecs AAC registration](https://www.w3.org/TR/webcodecs-aac-codec-registration/) · [WebCodecs Opus registration](https://www.w3.org/TR/webcodecs-opus-codec-registration/)

When WebCodecs lacks a capability needed by the precise route, a supported macOS source and target use AudioToolbox. An ordinary AAC encoder capability alone is insufficient if the browser cannot decode AAC for the priming measurement. A focused planning test covers this combination alongside an ordinary track in the same export.

The demuxer exposes the original lace anchor and member indices so signed block discard can cover several decoded packets. Its existing preroll API also respects a longer declared Matroska SeekPreRoll. Coarse source timestamps use integer coded duration and a source-tick residual range, with a packet-header scan before an interior seek; decode still begins at actual preroll. This preserves phase without treating every rounded packet timestamp as a new clock origin.

Actual Chrome integration with an injected encoder covers a delayed stereo start, a genuine gap, an unaligned trim across several conversion windows, exact sample counts, channel signal, metadata and cancellation. The separate real WebCodecs regression checks mono and stereo Opus and available AAC configurations, with PCM comparisons near both edges and a canceled stream that returns its source and closes the encoder. The packaged macOS mono workflow and the independent AudioToolbox AAC input probe passed on both architectures. The short multitrack macOS export has its own packaged check.

Run `node scripts/native-audio-export-smoke.mjs APP [FFMPEG_BIN]` with Chrome, FFmpeg and ffprobe. The tools decode generated fixtures independently of the packaged renderer. On Windows the preceding standard conversion produced 10,224 playable samples in WebM, 10,065 in 48 kHz MP4 and 9,803 in 44.1 kHz MP4 for the same 9,601-sample request. The packaged WebCodecs adapter produced exactly 9,601 samples in each case. The delayed track started 3,129 samples into the trim and retained 6,472 samples. FFmpeg independently decoded the intended signal on both sides of each trim at zero sample lag. The smoke checks channel counts, metadata, edited dimensions, source bytes, and both track presentations. FFmpeg raw AAC can include part of a padded packet beyond the MP4 edit. The test checks each edit's exact duration and the primary playback count in Chrome. Local Windows verification used the standalone FFmpeg and ffprobe 8.1.2 Essentials tools described in the timing record. CI provisions FFmpeg as a test tool. ## WebKitGTK Opus tail

The Linux native suite at `8f9f113` passed the edited frame checks and then failed WebM export because coded audio did not cover the selected samples. The runner used WebKitGTK `2.52.6-0ubuntu0.24.04.1` and GStreamer base `1.24.2-1ubuntu0.5`. An archived build on WSL Ubuntu with those same versions and a scoped count diagnostic reproduced the failure with 72,000 input frames, 312 OpusHead pre-skip frames, and 72,000 coded frames. The failure was 312 samples short of the requested presentation. [Linux job](https://github.com/stvlynn/OpenLR/actions/runs/42169194351/job/127732767234)

Independent WebKitGTK MiniBrowser tests used the real WebCodecs encoder and raw Opus decode to locate the final generated pulse. The tested encoder emitted only complete 960-frame blocks. Appending 312 silent samples still left a 72,000-sample selection short. Appending one complete block rescued that selection, but a 959-sample selection still lacked 311 audible samples. Two fixed blocks covered the tested selections and produced an extra block for a 313-sample input. Upstream WebKit's GStreamer audio encoder calls its harness flush, which processes queued output and then sends GStreamer flush-start and flush-stop events. That source explains the distinction between reading queued output and supplying a full block to the encoder. The counts and missing pulse above come from the installed runtime. [WebKit audio flush](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/gstreamer/AudioEncoderGStreamer.cpp#L331-L335) · [GStreamer harness flush](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/gstreamer/GStreamerElementHarness.cpp#L427-L450)

The browser Opus adapter now requests 20 ms packets and encodes one silent block using the same rate, channel count and encoder settings before the source stream. It reads the actual pre-skip and TOC duration and checks that they agree with the source encoder's output. Before flushing the source encoder it supplies only enough silence to reach the first complete coded packet covering the requested samples plus pre-skip. The submitted audible count excludes this silence. The muxer continues to omit complete trailing padding packets and stores the remaining discard on the last retained packet. [Opus WebCodecs registration](https://www.w3.org/TR/webcodecs-opus-codec-registration/)

The exact-padding candidate preserved the final pulse at its expected coded sample for eleven generated lengths between 240 and 72,001 frames on WebKitGTK. At 648 input samples the emitted packet ended exactly at the audible boundary after pre-skip. At 649 samples the encoder emitted two packets with 959 samples of trailing discard. At 72,000 samples it emitted 72,960 coded frames and retained the last pulse. The repaired `6f1d9b9` archive with this browser module passed the actual Linux MyGo video workflow, with VP9/Opus output, 64×96 rotated frames, both trim tones, unchanged workspace state and byte-identical originals. Its raw packet duration was 1.5135 seconds. The authored trim remained 1.5 seconds. Raw packet duration is distinct from playable audio length. The retained logs are `.workspace/webkit-opus-flush.log`, `.workspace/webkit-opus-exact.log` and `.workspace/webkit-opus-native-{baseline,exact}.log`.
