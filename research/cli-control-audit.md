## Confirmed viewport gap and resolution

The existing `zoom` command toggled fit/full resolution and state exposed its boolean. However, no command read or moved the detail scrollport, and neither full nor summary state reported its offset. A human could inspect other parts of a zoomed photo using native scrollbars while an agent could not request or verify the same view. Whole-image `preview` does not resolve that gap.

The added `viewport` command reads or sets absolute CSS-pixel offsets through the central dispatcher and the existing DOM scrollport. Both native scrollbar interaction and the command use the browser's one scroll state; no second pan model, transform or persisted recipe is introduced. The adapter reports actual offsets/dimensions and clamps to current extents. Full/summary state includes that snapshot; native scroll events notify the existing observation channel. Optional photo identity rejects a stale requested target before changing scroll position. Read-only calls neither scroll nor notify.

Primary API evidence: [Element.scrollLeft](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollLeft) exposes actual offsets including fractional CSS pixels; [Element.scrollTo](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollTo) supports explicit coordinates and instant behavior. Those semantics justify a DOM adapter, not claims about cross-platform execution. The browser/native tests must establish actual implementation behavior.

Context7 `/mdn/content` additionally confirmed `scrollWidth` and `clientWidth` include padding but exclude the vertical scrollbar, supporting the difference used for horizontal extent. It also records Safari overscroll behavior: reads report the actual DOM offset rather than inventing clamped observations, while explicit moves are bounded. OpenLR currently uses a left-to-right stage; this is not a generalized RTL scrolling adapter. macOS behavior still requires native acceptance.

The first Chrome acceptance checks discovery and dry-run typing, nonnegative validation, actual zoomed offsets, omitted-axis retention, bounds clamping, stale-target refusal, state readback, mouse-wheel changes and notification, unchanged recipe, fit bounds and Grid rejection. Native acceptance additionally checks actual CLI transport, PNG capture and original bytes. Test commands and measured platform outcomes belong in [acceptance](../docs/acceptance.md).

## Remaining audit scope

### Sequential grading input follow-up

The repair extends the existing `grading-set` operation with an exclusive single-field patch, checked against a required photo ID and canonical previous scalar. It merges at execution into the current recipe; full replacements and wheel gestures retain full grading guards. Numeric drafts retain their initial field expectation across unrelated redraws, and a pending local same-field value supplies the expectation for a subsequent local draft. A conflicting external value still fails rather than being overwritten. Focused dirty text survives redraw until commit/cancel or target/view changes. Existing validators and the same history/persistence path remain the owners of grading rules.

Context7 `/mdn/content` confirmed that [input events](https://github.com/mdn/content/blob/main/files/en-us/web/api/element/input_event/index.md) observe user edits while programmatic value assignment does not emit an input event; [change events](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlelement/change_event/index.md) represent commitment. This supports recording a draft before blur and avoiding redraw assignment over it, rather than expecting another change event to repair erased text.

A real Chrome 156 / Node 24.9.0 Windows ablation independently compared dispatcher values and IndexedDB records. Eight cases held only the completion notification of a real Balance -25 write and changed Blending to 80. Values below are final persisted Blending; Balance was -25 in every case. No synthetic save result, arbitrary delay or retry replaced storage. Baseline routed the `535d0f5` UI, draft-only retained full-snapshot submission, patch-only removed draft redraw protection, and combined used the repaired UI.

| Variant | Blur Blending before Balance completion | Blur after completion |
| --- | ---: | ---: |
| Baseline | 50 | 50 |
| Draft preservation only | 50 | 80 |
| Field patch only | 80 | 50 |
| Combined | 80 | 80 |

Both changes are needed: early blur requires field-scoped merging, late blur requires retaining input text. Ignored evidence is `.workspace/grading-numeric-ablation.mjs/.log`. The tracked `tests/color-grading-input.test.js` additionally covers successive same-field commits, undo/redo/reload, unrelated changes, real same-field conflicts, invalid patches, photo guards, and draft cancellation. This is correctness evidence, not a rendering-performance benchmark. The original failure and proposal record follows.

Windows run 42091276291 failed `color-grading-workflow.test.js:147`, waiting for Balance -25 and Blending 80 after adjacent numeric changes. A real Chrome 156 reproduction holds the completion callback of the actual IndexedDB photo write: Balance commits -25, then Blending is focused and filled with 80 before that callback is released. If Blending blurs first, both trusted change events fire but its full snapshot has the old expected grading value, so the dispatcher rejects the second change; final persisted values are -25/50 and a stale-edit notice appears. If Balance completes while Blending remains focused, redraw changes that unsaved DOM value back to 50; subsequent blur emits no second change and no notice appears. Both branches are asserted in ignored `.workspace/grading-numeric-race.mjs` with `.log`. The remote log cannot identify which branch caused its timeout.

This needs a product fix, not a test delay: numeric field updates could merge into the latest recipe through the central dispatcher with a photo identity and same-field expected-value guard, retaining full-snapshot guards for wheel gestures. Focused dirty numeric drafts must also survive same-photo redraws. An alternative is sequencing full snapshots against anticipated prior local results, but that adds predecessor/failure reconciliation and still needs draft preservation. These are proposals, not implemented behavior; no stale-edit protection was removed.

### Display-state and slideshow follow-up

The subsequent display-sampling implementation now closes the previously identified API and stale-click gaps through `point-sample`, while retaining canonical `sample-color`. Actual fixture comparisons, the held-save regression, pixel-coordinate API evidence and bounded video observation are recorded in [point sampling research](point-color-selection.md#display-sampling-follow-up-2026-11-06). The proposal paragraphs below describe the preceding audit; the new command contract is owned by [CLI documentation](../docs/agent-cli.md#point-color-selection).

The remaining point-sampling discrepancy has two distinct contracts: `sample-color` currently renders the committed edited recipe at edge 1280 and can be used outside the point tool; the GUI eyedropper reads the currently displayed canvas, whose resolution depends on viewport/DPR/zoom. Existing documented `sample-color` behavior should not silently change. A proposed shared `point-sample` action would read the published point-tool canvas and reuse point-add persistence/selection, while retaining explicit-hex point-add and canonical edited-image reads. This is not yet implemented. White balance is separate: its pointer maps back through geometry/optics to original coordinates and uses a decoded neighborhood; that algorithm should not be replaced by display sampling.

The point GUI currently reads hex before dispatch and does not bind that read to a published canvas owner. Selection can change while the previous canvas remains mounted during asynchronous drawing, so guarding only `active()` at click time is insufficient. A proposed implementation should associate the published canvas with the paint's photo/edit identity and reject stale clicked surfaces inside the shared command. Clipping is another boundary: entering the point tool clears it, but J can enable the overlay afterward. These source findings require a guarded runtime regression and a resolved display-sampling contract before implementation; they are not fixed by the compare transition below.

The command now exits crop as the existing `compare-pair` transition does. Existing paint cleanup removes the draft surface; no crop save or render rule was added. Tests verify original stage pixels and proportions, stored crop/processing version, original bytes, no extra history entry, comparison-off edited pixels, reopening crop and persistence.

The earlier slideshow fix covered explicit `view grid` only. A new real-Chrome regression failed when `grid-layout` entered Grid but left the session running. Cleanup now occurs in the shared `draw` path after selection reconciliation, covering all ways to reach Grid without duplicating transitions in each handler. The expanded test exercises layout, scope and no-match search, actual navigation visibility and timer advancement after exit; source changes and empty-selection reconciliation use that same path. This is a lifecycle rule, not an alternative slideshow renderer. Existing stop-in-detail behavior remains intact.

Inspection at `a70cb9b` found the clipping toggle absent from both full and summary state despite the GUI button and command using one internal flag. ## Review presentation defect

`sharing.reviews` previously displayed `JSON.stringify(result)` in the navigation panel. That exposed internal photo/comment/reviewer identifiers and protocol keys to a user trying to read feedback, contrary to the requested interface clarity. It now presents photo names, reviewer names, comment text, localized timestamps and like counts, without changing CLI result fields or server storage. Empty/revoked states are explicit. Unmatched historical photo IDs are labeled as unavailable photos instead of exposing IDs. Text uses DOM `textContent`, including comments that resemble HTML; no review markup is executed. The existing narrow navigation column wraps content and configuration inputs.

The new real-Chrome dispatcher test uses a clearly injected native boundary to verify structured return preservation, human-readable grouping, hidden internal IDs, inert HTML-like text, timestamps, empty/revoked results and no horizontal overflow. The 1024×768 screenshot was visually inspected after scrolling feedback into view. Native service acceptance remains a separate actual-server check. This fixes a presentation issue found during audit; it does not close the remaining complete gesture/command inventory or final delivery audit.

## Local stroke cancellation audit

Source inspection after `b9d4849` found that local tools handled `pointercancel` but not lost capture or Escape, and unmount removed listeners without clearing the shared draft. A real Chrome reproduction left the stroke coverage overlay after Escape and remount; it did not prove an erroneous persisted edit, so that stronger claim is not made. The first test's path selector was corrected to the actual SVG image coverage before recording the reproduction.

Context7 `/mdn/content` confirmed the [pointer capture lifecycle](https://github.com/mdn/content/blob/main/files/en-us/web/api/pointer_events/index.md) and [lostpointercapture event](https://github.com/mdn/content/blob/main/files/en-us/web/api/element/lostpointercapture_event/index.md). Capture is implicitly released after pointerup/cancel; explicit cancellation should release owned capture and clear the gesture. This is browser API evidence, not a Lightroom runtime observation. No competing image algorithm or new renderer is needed.

The existing UI adapter now owns one cancellation function for draft/capture cleanup, used by unmount, tool changes and pointer events. Escape invokes the discoverable `local-cancel` dispatcher command, including while an inspector input retains focus. A stale photo guard rejects before cancellation. Real mouse tests cover brush, both gradients, clone and heal, explicit CLI cancellation, real capture release, injected pointercancel, view/tool/panel changes, unchanged recipes and subsequent successful drawing/undo. Native smoke verifies the actual command transport and idle result; it is not native pointer-gesture evidence. Exact execution results remain in acceptance.
