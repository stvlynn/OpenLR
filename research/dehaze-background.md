# Background preparation for exact dehaze

Reviewed 2026-11-05 against the current source. This is an architecture proposal, not implemented or verified background behavior. The numerical operator and existing performance evidence remain in [dehaze research](dehaze.md). No external source or new image algorithm is needed for this review.

## What the current implementation does

`web/render.js` owns a `WeakMap` keyed by the immutable source frame or ImageBitmap. Each entry contains the latest source-correction key, corrected source and dehaze analysis. The key covers fills, red-eye, local tools and optics, but deliberately excludes dehaze strength, crop and output size. `dehazedSource()` currently performs `analyzeDehaze()` synchronously on a miss. Linear rendering then maps corrected source samples through `createDehazePixel()` before geometry interpolation; Original rendering maps before its existing canvas geometry. These stages must remain the only image implementation.

The measured exact analysis is still several seconds at 24 MP. `requestAnimationFrame()` does not move that computation off the main thread: the slider's `oninput` callback calls `paintStage()`, which calls `render()` and enters the synchronous miss. Current guards check the selected ID, bitmap ID, processing version and edit-object identity **before** rendering. Moving preparation behind a Promise requires checking these conditions again after the await.

There is no `web/codec-client.js` in this checkout. The reusable transport is `web/image-worker.js`, exported as `runImageWorker(url, message, transfers, fallback)`. Decode and encode call it through `web/decode.js` and `web/encode.js`; `web/codec-worker.js` is one particular codec adapter. The shared transport already:

- serializes jobs to bound simultaneous image heaps;
- waits for the worker's `ready` message before transferring buffers;
- distinguishes startup failure from a failure after handoff;
- permits a shared-kernel main-thread fallback only before handoff;
- terminates the worker on completion/error, renews its two-minute inactivity timer on progress, and records startup fallback diagnostics.

It currently has no AbortSignal, queued-job cancellation or consumer ownership API. The two-minute timer is an inactivity check, not a safe way to cancel obsolete work. A new private worker scheduler or a separate dehaze math implementation would duplicate existing responsibilities.

## Minimum preparation boundary

Add asynchronous `prepareDehaze(image, edit, options)` beside the existing renderer cache. It should return immediately for zero amount, await or create one pending entry for the same source-correction key, and resolve only when that entry has a usable corrected source and the required analysis. Keep `render()` / `renderFrame()` as the existing mathematical/rendering functions, and keep the synchronous path available to pure numerical tests. Production paths that can carry a nonzero amount must prepare before calling them; do not rely on a warm cache as an unstated precondition.

Use a thin `dehaze-worker.js` through `runImageWorker`. It imports and calls the existing `analyzeDehaze`, then returns the corrected frame and analysis. It must not implement new masks, sampling, correction or reconstruction. Adding dehaze to `codec-kernel.js` is less appropriate: that module eagerly imports codec material such as UTIF and owns decode/encode formats, whereas this task is an already-decoded frame operation. A separate thin worker adapter with the existing shared transport preserves that boundary.

The pending cache entry must be installed **before** asynchronous work starts. Later strength previews share that Promise rather than creating another worker. A negative-only request can prepare airlight without transmission; a later positive request upgrades once. If that upgrade is already in flight, subsequent negative previews also await it because the owned corrected buffer may be in the worker. A pending entry is never a renderable source.

On success, publish only if the entry is still the current entry for that source/correction revision. Replaced entries may fulfill an explicit snapshot consumer, but must not replace a newer cache entry or displayed image. On failure, clear the failed pending entry so a later explicit retry can recompute; do not leave a rejected Promise permanently poisoning the cache.

## Buffer ownership and cancellation

The original decoded frame/ImageBitmap remains on the main thread. Existing preparation already creates a corrected, owned Float32 source. Transfer **that** buffer after the worker handshake, then transfer it back with the transmission buffer in the result. The cache temporarily owns a pending entry, not an accessible detached frame. This avoids an additional 384 MB structured-clone copy at 24 MP. Never transfer the cached original's buffer. The worker should return both buffers with a transfer list; merely returning an object would clone them.

Successful handoff does not require a second original copy. Worker termination or runtime failure after handoff destroys the owned corrected copy; clear that entry and retain the original for a later retry. The existing startup fallback retains ownership because transfer has not yet happened. A fallback to the same synchronous analyzer preserves numerical results but loses responsiveness and must remain an explicit diagnosed limitation; it is not proof that every host supports nonblocking preparation.

Extend `runImageWorker` with an optional signal without changing existing callers. Check abort before constructing a queued worker, abort active work by terminating it, settle the Promise, remove listeners and release queued message/transfer references. Otherwise an aborted queued task can retain a full image until earlier jobs finish. Keep startup failure, processing failure, timeout and user/obsolete cancellation distinguishable. Do not run a fallback after transfer, after abort or after a domain-processing error.

Cancellation belongs to preparation consumers, not directly to one slider event. A preview that becomes stale may stop waiting immediately. Terminate its worker only when no explicit edit/export/thumbnail consumer still needs that same preparation. Coalesce successive strength events for the same source; aborting and restarting the identical analysis on every pointer move would make progress impossible. Selection/source-correction changes should drop obsolete preview ownership. `clearSources()` and bitmap replacement need to release their preview request and cache entry without invalidating an explicit export snapshot.

The first owned-source copy, source corrections and Original canvas-to-float conversion still happen before this proposed worker unless separately moved. They can take measurable time. The worker change must be described as background **analysis**, not as proof that every preparation stage or complete render is nonblocking. SharedArrayBuffer would require deployment/isolation changes and is not justified merely to avoid this existing copy.

`mask-preview.js` explicitly constructs a recipe containing only geometry/optics for its coverage rendering; it does not pass Dehaze and needs no dehaze preparation. Merge/enhancement output thumbnail calls that explicitly render `{}` are similarly neutral. The inventory should be rerun with `rg` after implementation, rather than treating every textual `render` occurrence as equivalent.

Most production callers already live inside async functions, so this boundary does not require a second renderer. Optional async wrapper functions can enforce preparation followed by the existing render operation, but they must not fork the stage sequence or ownership rules.

## Command and UI ordering

The central `run()` queue currently awaits `execute()`, and `execute()` awaits persistence, thumbnails and `draw()`. Keep explicit edits and exports serialized with their documented completion semantics. Uncommitted slider previews can prepare outside this queue and still reuse the same pending analysis when the committed edit arrives.

Moving analysis off-thread does **not** by itself let a selection command overtake an already queued edit that is awaiting its thumbnail. The event loop can process input, scrolling and a cosmetic draft, while serialized command completion still waits. If immediate selection during committed image processing is a product requirement, it needs a deliberate command/presentation scheduling change with target-captured mutations and capture/readback semantics; do not claim this smaller worker change solves that separate ordering issue.

The main thread must not retain an obsolete full-size temporary merely because an old preview Promise exists. Release request references on success, error and supersession. Exact analysis remains source-resolution and memory-costly: this proposal changes responsiveness and ownership, not its numerical footprint or prior's failure on bright clear surfaces.

## Acceptance before calling background work complete

1. Compare worker results against the synchronous analyzer exactly for generated haze, tiny/transparent frames, mixed alpha, signed/HDR data and negative-to-positive upgrades. Compare actual final pixels and existing source-coordinate crop/size tests.
2. In a real browser, start a fresh large-image analysis and measure event-loop/animation heartbeat while it runs. Move the slider repeatedly and verify a single preparation, latest draft displayed, no stale canvas flash and one committed undo entry. Report initial copy/correction delay separately from worker time.
3. Switch photos, change processing version/source corrections, enter comparison/crop mode and close the Local folder during preparation. Old results must never publish. Reopen and retry after a real worker error; verify unchanged original bytes and persisted state.
4. Exercise both an explicit command waiting on the same preparation and a stale preview releasing it. Ensure the required command is not accidentally canceled. Verify export cancellation, returned image/capture ownership and no early settings acknowledgment.
5. Test worker construction/module-load failure, failure after transfer, abort before handshake, queued abort and active abort. Confirm that original buffers remain attached, only owned buffers transfer, errors remain visible and rejected cache entries can recover. Extend the existing worker fallback tests rather than replacing their safeguards.
6. Measure total peak RSS, retained buffers, queue waiting time and warm/cold rendering on actual Windows WebView2 and Linux WebKitGTK. A browser heartbeat alone does not establish native support. macOS still requires its own actual execution.

No production files were changed by this review. The current synchronous cold path remains a known responsiveness gap until these implementation and acceptance steps exist.


## Implemented transport foundation

The shared runner now accepts an optional AbortSignal with queued/pre-handshake/active cancellation, prompt caller rejection and serialized completion of a running asynchronous fallback. A thin exact dehaze worker and owned-frame client use the existing queue and analyzer. Actual Chrome tests establish exact maps and unchanged returned source samples, preserved separate originals, active cancellation/retry and startup fallback. A generated 2048×1536 worker analysis took about 823 ms while a 10 ms main-thread heartbeat fired 82 times in that run. This is bounded adapter evidence, not proof that the application preview is nonblocking.

The preparation cache, UI request ownership and production caller wiring above remain unimplemented. The existing synchronous `render` path is unchanged by this foundation; do not relabel the previous 24MP interaction measurements as fixed. There is no new independent dehaze math or worker scheduler.

The installed pinned Mediabunny source confirms asynchronous video-export processing is supported: `node_modules/mediabunny/src/conversion.ts` declares `process` as returning `MaybePromise` (line 279) and forwards it to the transform (line 1892); `src/media-source.ts` awaits a promised processed result (line 460). This removes an API uncertainty for future `exportVideo` integration, but does not implement frame capture, cancellation or playback ownership in OpenLR.


## Production integration

`prepareDehaze`, `renderPrepared` and `renderFramePrepared` now share the renderer's source/correction cache and exact numerical functions. Pending consumers are counted; a canceled draft releases its claim, and a worker terminates only when the pending task has no consumers. Same-source slider updates join before releasing the preceding draft. Ready negative-only snapshots remain attached while a positive upgrade transfers a new owned copy. Results from replaced cache entries can satisfy their captured consumer without replacing the new entry. Failed entries are removed for retry.

All production consumers of nonneutral recipes were inspected and routed through preparation: app previews/thumbnails/histograms/sample colors/external output; normal/previous/batch export; imported/migrated/local/synced thumbnails; enhancement/share output; and awaited video-export processing. Mask coverage and neutral merge thumbnails keep their existing synchronous neutral calls. Playback awaits one captured paint before scheduling its next frame. UI publication checks request generation, selected photo, edit identity and detail mode after awaits; changing source or leaving detail aborts old preview ownership. Local folder changes abort thumbnail preparation and publication rechecks generation/recipe.

Batch export passes its existing signal through photo preparation; worker AbortError maps back to the original signal reason so cancellation retains existing partial-completion and cleanup semantics. An explicit queued edit still serializes command completion while its required thumbnail is prepared: background computation does not allow later mutation commands to overtake it.

The earlier transport-only and unimplemented-caller statements above describe the proposal/baseline. The application now uses background analysis; remaining large-image blocking comes from synchronous source preparation and reconstruction/encoding, especially Original. Current measurements are in [performance evidence](../docs/dehaze-performance.md). Native acceptance is recorded separately rather than inferred from Chrome.
