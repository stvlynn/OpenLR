# Preference restart evidence

The ARM64 job at da1c4bf passed the ordinary native suite, including guarded catalog operations, and all three independent short-audio checks. Its separate default-store check failed after a restart: the setter had returned filenames false, but the reopened host returned true. The other preferences matched. The assertion preceded reopened catalog assertions, so this failure does not establish whether those records persisted. The owned reopened host was responsive: readiness at 2,518 ms, failure at 3,128 ms, matching session, health 200 and a responding control lane. The UI probe returned 404, rather than a measured UI-pump result. Windows, Linux and Intel macOS completed their jobs successfully. [ARM64 job](https://github.com/stvlynn/OpenLR/actions/runs/42221923590/job/127905843695)

At da1c4bf the application assigned the validated preferences object and called localStorage.setItem synchronously. The default-store smoke sets filenames immediately before restarting. Its helper sends the first SIGTERM and waits for exit. Pinned MyGo 0.7.4 documents and implements that first signal as its normal Quit sequence; a second signal exits immediately. This was not a recorded SIGKILL or deliberate hard-crash test. The current log does not show the WebKit storage-process flush or the preference file contents. [MyGo lifecycle](https://github.com/egoist/mygo/blob/v0.7.4/app.go)

Current upstream WebKit SQLiteStorageArea starts a transaction for writes and schedules commit after 500 ms. Its close path also commits, and LocalStorageManager has a separate syncLocalStorage operation. These are source observations from upstream main, not proof that the runner followed a particular branch or that a delay would fix the application. No sleep, replay or relaxed restart assertion has been added. [SQLite storage](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/storage/SQLiteStorageArea.cpp) · [Local storage manager](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/storage/LocalStorageManager.cpp)

Context7's /mdn/content documentation distinguishes IndexedDB transaction completion from the durability hint. Strict durability requests confirmation of writes to persistent storage; relaxed durability permits completion after handing writes to the OS. Neither implies immunity to every storage failure. This gives a concrete alternative to evaluate against the existing storage path. A host-managed settings file would instead place ownership in the OS adapter and needs migration, isolated test profiles and visible write errors. These were the candidate designs before the comparison and implementation recorded below. [Transaction durability](https://github.com/mdn/content/blob/main/files/en-us/web/api/idbtransaction/durability/index.md)

The investigation below compares acknowledged writes and immediate reopen in actual native hosts, retaining failed trials and distinguishing a localStorage flush hypothesis from origin/profile or load errors. The original default-store assertion remains required.

## Isolated comparison

The manual [42226895345 comparison at e0743f5](https://github.com/stvlynn/OpenLR/actions/runs/42226895345) completed all eight trials on both macOS architectures. ARM localStorage trial index 4 acknowledged filenames false, but the next process read the previous stored true value (the record was present). Its four strict IndexedDB trials all retained the values. Intel passed all eight. ARM strict write times were 77/31/38/23 ms; Intel 65/31/21/23 ms. localStorage acknowledged in 0 ms on ARM and 1/0/0/0 ms on Intel. The ARM workflow correctly failed after retaining all trials; Intel succeeded. These are measured browser timestamps, not throughput benchmarks. The last ARM localStorage write of true followed the failed false write and was therefore already equal to the persisted value; it is not evidence of a successful changed-value flush. No retry replaced the failed trial.

This result motivates [the catalog settings decision](../docs/decisions/021-preference-persistence.md). The implementation now uses the existing database with strict settings transactions, waits before publishing changes, and migrates legacy values only when no catalog setting exists. Native validation of the integrated implementation is separate from the isolated candidate results.

At e0743f5, `scripts/fixtures/preferences-probe` served the actual production preferences module for the localStorage candidate and a four-boolean IndexedDB record for the strict transaction candidate. The fixture now freezes that e162e9d localStorage load/set behavior so production changes cannot silently change the comparison baseline. `scripts/native-preferences-probe.mjs` runs eight trials in ABBA/ABBA order. Each backend requests false/true/false/true. Each write is followed by an immediate normal MyGo Quit and a fresh host read. The report checks both returned state and the stored record; absent records cannot pass by matching defaults. IndexedDB writes must acknowledge strict durability. There is no settling sleep or trial retry; failures remain in the output and fail the run after the scheduled comparison finishes.

The host uses one persistent profile throughout. Windows WebView2 and Linux environment paths are isolated in an owned temporary directory; macOS uses the default WKWebView data store on a fresh disposable Actions account. Do not run this macOS diagnostic on a personal account expecting directory-level WKWebView isolation. The fixture requests Quit directly after writing its report, whereas the original application smoke receives a CLI response and sends SIGTERM. This isolated comparison does not recreate the preceding full catalog workflow or prove a cause for that failure.
