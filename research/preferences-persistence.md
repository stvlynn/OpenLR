# Preference restart evidence

The ARM64 job at da1c4bf passed the ordinary native suite, including guarded catalog operations, and all three independent short-audio checks. Its separate default-store check failed after a restart: the setter had returned filenames false, but the reopened host returned true. The other preferences matched. The assertion preceded reopened catalog assertions, so this failure does not establish whether those records persisted. The owned reopened host was responsive: readiness at 2,518 ms, failure at 3,128 ms, matching session, health 200 and a responding control lane. The UI probe returned 404, rather than a measured UI-pump result. Windows, Linux and Intel macOS completed their jobs successfully. [ARM64 job](https://github.com/stvlynn/OpenLR/actions/runs/42221923590/job/127905843695)

The application currently assigns the validated preferences object and calls localStorage.setItem synchronously. The default-store smoke sets filenames immediately before restarting. Its helper sends the first SIGTERM and waits for exit. Pinned MyGo 0.7.4 documents and implements that first signal as its normal Quit sequence; a second signal exits immediately. This was not a recorded SIGKILL or deliberate hard-crash test. The current log does not show the WebKit storage-process flush or the preference file contents. [MyGo lifecycle](https://github.com/egoist/mygo/blob/v0.7.4/app.go)

Current upstream WebKit SQLiteStorageArea starts a transaction for writes and schedules commit after 500 ms. Its close path also commits, and LocalStorageManager has a separate syncLocalStorage operation. These are source observations from upstream main, not proof that the runner followed a particular branch or that a delay would fix the application. No sleep, replay or relaxed restart assertion has been added. [SQLite storage](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/storage/SQLiteStorageArea.cpp) · [Local storage manager](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/NetworkProcess/storage/LocalStorageManager.cpp)

Context7's /mdn/content documentation distinguishes IndexedDB transaction completion from the durability hint. Strict durability requests confirmation of writes to persistent storage; relaxed durability permits completion after handing writes to the OS. Neither implies immunity to every storage failure. This gives a concrete alternative to evaluate against the existing storage path. A host-managed settings file would instead place ownership in the OS adapter and needs migration, isolated test profiles and visible write errors. These are candidate designs; no persistence change has been made yet. [Transaction durability](https://github.com/mdn/content/blob/main/files/en-us/web/api/idbtransaction/durability/index.md)

The next investigation must compare acknowledged writes and immediate reopen in actual native hosts, retaining failed trials and distinguishing a localStorage flush hypothesis from origin/profile or load errors. The original default-store assertion remains required.

## Isolated comparison

Windows x64 executed all eight trials successfully (16 fresh native processes). localStorage write acknowledgments took 0.10/0.10/0.20/0.10 ms; strict IndexedDB acknowledgments took 51.30/16.80/17.20/17.80 ms. All reopened records matched, including explicit record presence. These timings are observations, not performance gates or evidence for macOS. The fixture compiled for Darwin amd64 and arm64; compilation is not native execution. Eight probe evidence/lifecycle tests passed, and the fixture passed Go compilation and vet (no Go unit tests). Local JSON and detailed logs are ignored under `build/preferences-report.json` and `.workspace/preferences-probe-windows.log`.

The subsequent full application run [42224648105 at e162e9d](https://github.com/stvlynn/OpenLR/actions/runs/42224648105) passed all four platforms, including both macOS default-store restart checks. Production preference storage was unchanged. This establishes a later successful restart, not a cause or fix for the earlier ARM failure.

`scripts/fixtures/preferences-probe` serves the actual production preferences module for the localStorage candidate and a four-boolean IndexedDB record for the strict transaction candidate. `scripts/native-preferences-probe.mjs` runs eight trials in ABBA/ABBA order. Each backend alternates false/true/false/true, so later writes cannot pass simply by preserving an earlier value. Each write is followed by an immediate normal MyGo Quit and a fresh host read. The report checks both returned state and the stored record; absent records cannot pass by matching defaults. IndexedDB writes must acknowledge strict durability. There is no settling sleep or trial retry; failures remain in the output and fail the run after the scheduled comparison finishes.

The host uses one persistent profile throughout. Windows WebView2 and Linux environment paths are isolated in an owned temporary directory; macOS uses the default WKWebView data store on a fresh disposable Actions account. Do not run this macOS diagnostic on a personal account expecting directory-level WKWebView isolation. The fixture requests Quit directly after writing its report, whereas the original application smoke receives a CLI response and sends SIGTERM. This isolated comparison does not recreate the preceding full catalog workflow or prove a cause for that failure.

Build with `go build -tags mygo_noinspector -ldflags '-X github.com/egoist/mygo.production=1' -o build/preferences-probe ./scripts/fixtures/preferences-probe`, then run `node scripts/native-preferences-probe.mjs build/preferences-probe build/preferences-report.json` (use an `.exe` filename on Windows). The manual `macos-preferences-persistence.yml` workflow runs Intel and ARM hosts and retains JSON artifacts even on failure.
