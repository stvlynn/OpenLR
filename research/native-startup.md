# Native startup timeout evidence

The Windows job of [`3163f36`, Actions 42103142177](https://github.com/stvlynn/OpenLR/actions/runs/42103142177) built successfully and passed browser verification (338/346, eight optional-resource skips). The first native `state --summary true --timeout 30` failed at that revision's `scripts/native-smoke.mjs:429`. It had not imported a photo or exercised the new white-balance commands. Linux and macOS Intel completed their native suites. The Windows log contains no command receipt, renderer navigation or catalog readiness observation; it does not establish a product root cause.

Source inspection distinguishes four boundaries. `main.go` calls `startAgent` after MyGo readiness and the instance lock, before opening the window. `agent.go` publishes its session after binding the loopback listener. A valid session therefore does not establish that the WebView loaded. `web/agent.js` polls commands through MyGo IPC; ordinary `app.run` waits for catalog/preset reads and initial drawing. `export-status` instead uses the separate control poll and bypasses that readiness promise. Neither the existing startup error listener nor the failure log proves which of these later stages stalled.

The native smoke now gathers evidence only after its existing startup assertion fails and before host cleanup. It retains the original error and deadlines. It records elapsed launch/session/request times and child PID/exit state, validates the descriptor using the existing CLI `connect`, and confirms that its PID belongs to the spawned child before sending probes. It then concurrently sends one authenticated `/health` request and one read-only `export-status` command. Each network probe has a two-second deadline. It does not retry `state`, change application startup or make a failed test pass. Asynchronous spawn errors also enter this path; cleanup failures are reported separately without replacing the initial error.

| Observation                       | What it establishes                                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Health and control both respond   | Broker and renderer control round trip work at diagnostic time; investigate ordinary delivery/readiness next. |
| Health responds, control does not | Broker is reachable; renderer loading, IPC or control dispatch still needs evidence.                          |
| Health does not respond           | Broker/process/loopback remains unresolved; do not infer a catalog or image-processing error.                 |

These are observations taken after the original deadline. A later working probe cannot prove the same path worked during the failed request. Diagnostics log only allowlisted status, timing and process fields: no descriptor/token, endpoint, workspace result, photo name, profile or environment dump. If these probes remain insufficient, the next justified step is timestamped renderer/navigation and poll/delivery milestones under the existing diagnostics switch, rather than a speculative timeout increase.

`node --test tests/native-startup-diagnostics.test.js` passed 4/4 on Windows / Node 24.9.0. It uses a real local HTTP server with controlled responses, not a native GUI: checks include authenticated health/control requests, no ordinary-state replay, returned-data omission, an unresponsive control path, invalid-session refusal and a mismatched process ID. An actual missing-executable launch also printed the sanitized diagnostic and retained the original `ENOENT` with exit 1. This validates the diagnostic mechanism, not the unresolved startup failure.

The subsequent panel revision `0c030e5` completed [Actions 42105066362](https://github.com/stvlynn/OpenLR/actions/runs/42105066362) successfully on all three platforms at its first attempt, before these diagnostics were added. It is a new successful execution, not evidence that the earlier timeout's root cause was repaired.

## Navigation, renderer and delivery milestones

The Windows job for `3dbc68d` reached its first native state request after 133 ms. The 30-second request timed out. The failure probe found a live process, a matching session and HTTP 200 from the authenticated broker. Its independent control request also timed out. These observations narrow the boundary to the renderer, IPC or control dispatch. The original log is retained in `.workspace/expanded-ci-windows.log`.

`OPENLR_DIAGNOSTICS=1` now emits the first occurrence of each startup stage with elapsed monotonic milliseconds in the host. The suite already sets this switch. MyGo v0.7.4 invokes `App.OnWindowCreated` before `loadPage`. That callback attaches navigation, DOM, load completion, load failure and renderer-loss observations without intercepting navigation or changing window options. MyGo reports DOM readiness through its own bridge notification. Renderer milestones also require IPC delivery, so absence alone cannot prove that a script did not run. [MyGo window lifecycle](https://github.com/egoist/mygo/blob/v0.7.4/window.go) · [Page event contract](https://github.com/egoist/mygo/blob/v0.7.4/docs/windows.md) · [Bridge dispatch](https://github.com/egoist/mygo/blob/v0.7.4/bridge.go)

| Observed milestone boundary                                                                          | Evidence                                                                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent-published` → `window-requested` → `window-created`                                            | Broker session was published and MyGo created a native window before initiating the page load.                                                                                                                                                                |
| `navigation-committed`, `load-finished` or `load-failed`, and `renderer-gone`                        | MyGo reported a navigation, a load outcome or renderer loss.                                                                                                                                                                                                  |
| `renderer-script`, `renderer-agent-ready`                                                            | The early script or the evaluated agent module sent its fixed marker to Go.                                                                                                                                                                                   |
| `catalog-read-started` → `catalog-read-finished` → `workspace-ready`                                 | Initial catalog reads and the first draw completed as their milestones arrive. A failure reports `workspace-ready-failed` and preserves the visible error.                                                                                                    |
| Lane `http-received` → `poll-delivered` → `renderer-received` → `dispatch-finished` → `http-replied` | The ordinary or control command passed each separate boundary. `poll-entered` shows its IPC request reached Go even with no command yet. A dispatch can finish with an error envelope. `http-replied` means the broker wrote the response to its HTTP writer. |

The early script also sends a fixed `renderer-script-failed` marker and retains the original visible startup notice. Renderer markers are fire-and-forget and carry only their stage identifiers. The host logs the fixed identifiers and elapsed time. Milestone times reflect when Go observed them, so concurrent bridge calls can appear in a different order from JavaScript dispatch. These are first-occurrence lane observations, not correlated command traces: if requests overlap or expire, different stages can belong to different requests. The host writes bounded records synchronously to stderr; the pending-IPC test does not prove independence from a blocked stderr consumer. Existing startup deadlines and the failure-only health/control probes retain their original behavior.

The packaged Windows build `build/startup-trace/windows-amd64/OpenLR.exe` passed an isolated native probe on Windows build 26200, Node 24.9.0 and WebView2. It completed the ordinary `state` and control `export-status` commands. The broker published at 23 ms, the window was created at 51 ms, navigation committed at 696 ms and the renderer reported its early script at 710 ms. Both polls reached Go at 937 ms. Catalog reads finished at 1,018 ms, the workspace was ready at 1,024 ms, and ordinary and control HTTP replies were written at 1,029 ms and 1,052 ms. The build and probe logs are `.workspace/startup-trace-build.log` and `.workspace/startup-trace-windows.log`. This run validates the timeline on working startup. The earlier timeout remains unresolved.

Run `node --test tests/startup-milestones.test.js tests/native-startup-diagnostics.test.js` for the browser and loopback checks. All seven passed. The controlled Chrome bridge leaves diagnostic IPC pending while normal commands complete, holds and then rejects catalog startup while control still replies, and blocks an early module while preserving the visible notice. The four targeted Go tests passed with `go test . -run 'Test(StartupRendererMilestones|Agent|ExportControls)' -count=1 -v`. They check that unrecognized or repeated renderer messages never enter the trace and that control can reply while an ordinary command remains held.

The child PID matched the valid session, the authenticated health request returned 200, and the independent control request reached the broker at 30,108 ms but also expired. The retained log is `.workspace/video-frame-ci-windows.log:703–714`. For comparison, `f6af855` first recorded window creation at 750 ms and navigation commit at 8,000 ms, then completed the suite. Its later windows reached navigation in 463–1,381 ms from startup. The retained success log is `.workspace/startup-trace-ci-windows.log:700–1267`.

The three retained Windows logs with a first-state timeout (`3163f36`, `3dbc68d`, `7338f7f`) report runner version `20261021.618` and `windows-2025-vs2026` image `20261030.294.1`. The `f6af855` success used runner `20261103.629` and image `20261103.298.1`. Runs for `535d0f5`, `a84b5b5`, `ca1299b`, and `daf0a11` also completed their Windows native suites on the older runner and image. This association comes from retained runs, and the actual WebView2 runtime versions were not captured. The observations do not establish that either image or its runtime caused the timeouts.

The pinned MyGo v0.7.4 source separates native window construction from WebView2 readiness:

- `window.go:548–578` assigns the native window, calls `OnWindowCreated` synchronously, then calls `loadPage` and shows the window. `events.go:81–91,141–145` registers and invokes Go listener functions. OpenLR's `startup_diagnostics.go:38–46` records entry and attaches five listeners. It does not call a page operation or wait for the renderer. [Window creation](https://github.com/egoist/mygo/blob/v0.7.4/window.go#L548-L578) · [Listener implementation](https://github.com/egoist/mygo/blob/v0.7.4/events.go#L81-L145)
- On Windows, `internal/windows/window.go:132–137,247–250` starts the environment and schedules controller creation. `internal/windows/app.go:198–229` invokes the waiters when the asynchronous environment callback arrives. `internal/windows/webview.go:61–85,121–161,326–344` queues page work until the controller is ready and drains it at `becomeReady`. A `window-created` mark therefore establishes that native creation returned and the observer began. It leaves controller readiness and the actual navigation unobserved. [Windows window setup](https://github.com/egoist/mygo/blob/v0.7.4/internal/windows/window.go#L132-L250) · [Environment callback](https://github.com/egoist/mygo/blob/v0.7.4/internal/windows/app.go#L198-L229) · [Controller and pending navigation](https://github.com/egoist/mygo/blob/v0.7.4/internal/windows/webview.go#L61-L161)
- `internal/windows/webview.go:240–242,362–390,660–665` maps `ContentLoading` to the commit event and discards the immediate `Navigate` HRESULT. `window.go:1735–1740,1876–1897` confirms that `OnWillNavigate` cannot trace this programmatic first load. The missing commit leaves multiple possible stops, including an outstanding environment or controller callback, UI-thread blockage, immediate navigation failure, or an embedded resource response that has not completed. Microsoft documents that WebView2 callbacks depend on the STA UI thread's message pump. [Windows navigation](https://github.com/egoist/mygo/blob/v0.7.4/internal/windows/webview.go#L660-L665) · [MyGo navigation callbacks](https://github.com/egoist/mygo/blob/v0.7.4/window.go#L1735-L1746) · [WebView2 threading model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/threading-model)

The opt-in trace now records `window-observers-attached` after listener registration and `window-request-returned` immediately after `NewWindow` returns. A return on Windows still leaves actual controller and navigation progress to WebView2's callbacks.

After the original state deadline, the existing failure helper sends an authenticated request to `/diagnostics/startup-ui` concurrently with its health and control probes. With `OPENLR_DIAGNOSTICS=1`, the broker posts one callback per host through MyGo's public `RunOnMain` from a goroutine. The callback signals completion without performing IPC or logging on the UI thread. The broker waits up to one second inside the failure helper's existing two-second window. A positive response shows that a task was dispatched on the UI thread during the diagnostic window. A negative response shows that the callback was not observed during the bounded wait. HTTP 404 identifies an unavailable probe endpoint, including older packages. This keeps the original state failure, sends no replay, and schedules no background probe during ordinary startup. MyGo does not expose cancellation for the queued callback, so one goroutine may remain waiting until dispatch or host exit. [MyGo main-thread dispatch](https://github.com/egoist/mygo/blob/v0.7.4/loop.go#L81-L108)

MyGo v0.7.4 exposes WebView availability and a page user agent. These APIs do not report the selected WebView2 runtime version, so the diagnostics leave it unreported. [Availability contract](https://github.com/egoist/mygo/blob/v0.7.4/internal/windows/webview2.go#L357-L373) · [Page user agent API](https://github.com/egoist/mygo/blob/v0.7.4/window.go#L1419-L1426)

## WebView2 backend trace

The Windows `f9cb4ba` job passed the main, sync, and file-open workflows. The following organization host returned from `NewWindow` in 43 ms but had no navigation commit before the ordinary state timeout. The authenticated health probe returned 200. The UI probe completed in 7 ms while the renderer control probe expired. The UI thread could dispatch the diagnostic callback at failure time, which leaves WebView2 setup and navigation unresolved. The log is `.workspace/pause-clock-ci-windows.log`. [Actions run 42157628028](https://github.com/stvlynn/OpenLR/actions/runs/42157628028)

On Windows, build and run a separate diagnostic package with the normal MyGo packager and an instrumented copy of the pinned dependency.

```powershell
node scripts/native-startup-build.mjs
node scripts/native-suite.mjs build/startup-diagnostic/windows-amd64/OpenLR.exe
```

The builder checks the pinned MyGo version and checksum, verifies the module cache, and applies the tracked patch to a private copy. A temporary Go module file selects the copy only for the diagnostic build. Go overlays cannot replace files beneath `GOMODCACHE`. The diagnostic package has a separate output directory. [Go build overlay constraints](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies)

The trace records environment and controller call returns and callbacks, controller setup, queued navigation release, `Navigate` return, native navigation events, and the first embedded document request and response. Each event records a fixed stage name, elapsed milliseconds, HRESULT, a stage-specific numeric detail, and the total dropped messages. The UI thread puts records on a 64-entry queue without waiting for stderr. A saturated queue can lose events, and process exit can leave queued records unwritten. The backend clock starts during package initialization, while the host milestone clock starts in `main`. The trace fields omit URLs, paths, headers, bodies, tokens and COM pointers. [WebView2 navigation events](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/navigation-events)

The local instrumented Windows build reached the ordinary state and preferences requests in a disposable profile. It recorded the queued `LoadURL`, release of two pending calls, successful `Navigate`, the first embedded document's HTTP 200 response and successful navigation completion. It reported zero drops. The local launch did not reproduce the remote failure. Its log is `.workspace/webview2-startup-local.log`. `node --test tests/native-startup-build.test.js` verifies scratch cleanup on success and failure and rejection of redirected staging.

The Windows workflow builds and runs this separate instrumented package only after the ordinary native suite fails. The original step and job remain failed. This changed diagnostic experiment supplies additional backend observations; a successful instrumented run does not replace the failed production result.

The `d397439` ARM macOS main workflow lost its broker connection during the later 2400×1800 viewport image import after its export-control checks had passed. The job did not report a host exit code at that boundary, so a crash or renderer failure is not established. This observes process state, broker health, renderer control and the UI callback without replaying the failed operation. Existing diagnostic tests pass 5/5; another actual failure is needed to establish its runtime cause.

## Post-readiness disconnect during macOS depth verification

In the ARM64 `8f9f113` job, the depth host recorded workspace readiness at 05:37:48.622 UTC and completed its first HTTP reply at 05:37:48.632. The workflow announced first-use depth provisioning at 05:37:50.095. After the awaited depth-estimate command returned, the next recipe state read at `native-depth-smoke.mjs:69` received `ECONNREFUSED` at 05:37:57.219. The job exit code 1 belongs to the test runner. The shared host helper recorded startup failures and had no post-readiness exit report, so this log leaves the host's actual exit status and cause open. The retained log is `.workspace/8f9f113-arm-depth-ci.log`. [ARM64 job](https://github.com/stvlynn/OpenLR/actions/runs/42169194351/job/127732767186)

The shared native workflow helper now records the launched child's exit code or signal and elapsed time before cleanup. After a ready-workflow failure, it runs the existing bounded broker, control and UI probes and allows up to 250 ms to observe a pending exit event while those probes run. On macOS, an observed exit triggers a two-second scan for a recent matching `.ips` crash report in the user and system diagnostic directories. The collector checks the report type, process name, PID and timing. It reads at most 2 MiB per candidate and reports exception, termination and up to six filtered frames. It leaves full reports, paths, application messages and credentials out of the output. The workflow still fails with its original error and sends no command replay. [Node child exit event](https://nodejs.org/download/release/v24.9.0/docs/api/child_process.html#event-exit) · [Apple crash report fields](https://developer.apple.com/documentation/xcode/interpreting-the-json-format-of-a-crash-report)

`node --test tests/native-startup-diagnostics.test.js` passed 7/7 on Windows. The new tests observed a real controlled child exit after readiness, preserved the original failed command and filtered generated crash reports by process and time. Actual macOS report discovery and the cause of the depth disconnect remain open.
