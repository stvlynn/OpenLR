## Proposed domain and defaults

Use one recipe owner `colorGrading`, containing `shadows`, `midtones`, `highlights`, `global`, `balance` and `blending`. Each wheel stores finite `hue` in[0,360], `saturation` in[0,100], and `luminance` in[-100,100]. Canonicalize 360 to 0. Missing wheels have hue 0, saturation 0, luminance 0; balance defaults 0, blending 50. Reject out-of-range values rather than silently altering malformed recipes. A wheel hue is the tint direction; saturation is tint strength, not multiplication of the image's existing saturation. Hue alone does not alter pixels.

A recipe with every saturation and luminance zero is visually neutral regardless of hue/balance/blending. Compile it to no operation. Preserve dormant hue choices if desired for interaction, but the Edited filter must use this shared neutrality test instead of treating any object as a visible adjustment. Reset returns defaults; resetting a wheel must preserve the other wheels and shared balance/blending. Keep `colorGrading` as one selective-copy key and one independently serializable domain owner. Versions, presets, undo, sync and export should reuse existing recipe pathways.

## Independent mathematical contract

All image calculations below are in existing linear sRGB coordinates. Define `Y = .2126R + .7152G + .0722B` from the immutable input to this stage. Alpha does not enter the calculation.

For masks, let `z=max(0,Y)`, `p=.18*2^(-balance/50)` and `t=z/(z+p)`. Construct `a=[(1-t)^2, 2t(1-t), t^2]`, raise each component to `q=4-3*blending/100`, then normalize their sum. These are the shadow, midtone and highlight weights. They are nonnegative and sum to 1. Increasing balance gives highlights more influence; increasing blending widens overlap. Negative luminance gets shadow weight; HDR tends smoothly toward highlights. Only the mask coordinate is bounded/compressed: RGB samples are never clipped. Global weight is independently 1 and is not part of this partition.

To construct a hue direction, take the standard six-sector full-saturation/value sRGB hue-wheel color, decode its components with the existing sRGB transfer function, subtract its linear Y from each component, and divide by the maximum absolute component. This direction has zero Rec.709 luminance. This is an independently defined RGB tint geometry; it is not a perceptually uniform hue space or darktable UCS. Use the exact same definition for displayed wheel hue and processing, while recognizing that a bounded display cannot show every resulting graded color.

For each of the four wheels, accumulate `weight * (saturation/100) * .25 * direction`. The shared strength factor .25 is an explicit initial product choice, not a result fitted to Lightroom. Set input scale to `max(abs(R),abs(G),abs(B))` and add scale times the accumulated vector to RGB. Using one input scale and one input mask calculation prevents wheel ordering from changing the result. It avoids divisions by pixel luminance near zero and retains tint influence on signed chromatic samples. Exact black stays black. This operator adds tint while preserving linear Y within floating-point error; it does not claim constant perceived brightness or hue preservation of the original color.

Separately accumulate `stops = sum(weight * luminance/50)` across the three regions plus global. Multiply the tinted RGB by `2^stops`. Thus chroma-only controls preserve Y, while luminance controls intentionally change it. This gain is positive and finite for the bounded settings, preserves channel ratios when tint is zero, does not clip negative values, and does not lift exact zero. Regional luminance 100 represents up to+2 stops; global can add another+2. This is an exposure-like luminance control, not an additive black-point adjustment. Document that behavior explicitly.

The chosen scene-luminance mask response is independent of image maxima: the same pixel and edit produces the same result regardless of crop/neighboring pixels. Do not normalize masks against per-photo histograms. It is continuous at zero but does not promise equal derivatives on both sides because `max(0,Y)` defines the negative-luminance policy.

## Pipeline and interaction integration

Place grading after existing curve and HSL/point-color stages and before spatial effects. The stage then sees the current edited colors and tonal distribution, without changing existing operation order when grading is neutral. Legacy byte rendering decodes its current RGB samples to linear, invokes the same domain operation, and quantizes only when writing the byte buffer. Linear rendering invokes it directly on float samples. Neither path changes alpha. Do not route Linear through a byte canvas, clamp intermediate float RGB, or mutate cached originals. Keep the old no-adjustment fast path aware of nonneutral grading.

Expose shadows/midtones/highlights/global choices with hue/saturation wheels and a separate luminance control, plus shared balance/blending. Provide numeric/keyboard alternatives for each wheel; pointer drag must use the shared dispatcher with asset/revision ownership and one coherent undo result. Saturation zero centers a wheel while retaining a chosen hue for later movement. Product labels belong to the shared message owner; implementation explanations stay in documentation, not the editing UI.

Required verification includes exact neutral identity and untouched old recipes; mask sums/balance/blending; chroma-only Y conservation; signed/HDR continuity and finite outputs; alpha/source immutability; wheel/control keyboard and drag interaction; cancellation and source changes; undo/reload/preset/version/selective-copy; both processing versions; and decoded export pixel checks. Synthetic evidence here is not a substitute for actual native WebView and end-to-end image tests.

Brightness conservation above applies to the floating chroma-only stage before output conversion. Display/export gamut clipping and byte quantization can change measured output luminance; tests must separate that expected output boundary from errors in the shared operation. The proposal does not prove image quality on real photographs. Before accepting the implementation, inspect generated neutral ramps, saturated color patches and a licensed photographic fixture, and report any visible clipping or hue limitations without claiming perceptual uniformity.
