# High-precision image pipeline audit and migration proposal

Source audit on 2026-11-05, against `b8b9bab7b31a66edaf137a7e92ccdae1bc3c6e4f`. Line references describe that revision. This is an implementation proposal, not a new product requirement or a report of runtime validation. No competitor behavior establishes requirements here.

## Finding and recommended first implementation

The current ordinary editor cannot retain source precision or gamut through to export. `decodePhotoLinear` and the scalar floating-point color transforms are useful building blocks, but ordinary preview/export still consume an `ImageBitmap`, and every active image-edit stage uses an 8-bit canvas or byte array. Converting that final surface to ProPhoto or writing it in a 16-bit container cannot recover the discarded values.

The highest-value first complete feature is **one high-precision still-photo path through the existing renderer, from a real 16-bit wide-gamut decode to a true 16-bit ICC-tagged TIFF export, with every existing still edit participating**. Preview is a terminal view of the same edited frame. Start with generated 16-bit TIFF plus the existing real LibRaw path, rather than a float object consumed only by an isolated test or an export shortcut. This requires porting the render stages below; it is a bounded vertical feature, but larger than adding a new frame type. Do not call a phase complete while a supported edit silently falls back to a full-image 8-bit canvas.

An earlier, independently useful commit can establish the frame/transform/serializer contract and its numerical tests, provided documentation calls it infrastructure. In particular, changing `convertSrgbPixels` to accept floats while `encodePhoto` still calls `getImageData` is infrastructure, not a high-precision export.

Preserve old recipes with an explicit processing version. Both versions must use one render-stage scheduler and the existing dispatcher. A version chooses source decoding, stage parameters, domain conversions and, where needed, legacy quantization. It must not introduce a second simplified renderer that omits repairs, masks, geometry or spatial effects.

## Actual entry points and order

- `web/decode.js:69` (`decodePhotoLinear`) is RAW-only, used by HDR and DNG. `web/decode.js:84` (`decodePhoto`) returns the ordinary video poster or raster/RAW bitmap. `web/app.js:155` (`source`) caches that surface by photo ID, resolves local/catalog/migrated originals, and owns closing the previous bitmap/video.
- `web/render.js:16` (`render`) computes output geometry and source preview scale, then runs fills → red-eye → local repairs → depth blur → local masks → optics/TCA → crop/quarter-turn/flip/resize → global tonal color → curve → HSL/point color → spatial effects. `applyLocalTools` owns the repair/blur/mask suborder. This order is part of the existing look.
- `web/app.js:278` (`paintStage`) calls `render` for normal, original-comparison and paired views; `web/app.js:1663` calls it for agent preview and rendered export. Export adds a watermark and calls `encodePhoto`. Import thumbnails (`web/import-library.js:74`), local thumbnails (`web/local.js:120`), updated thumbnails (`web/app.js:507`), enhancement (`web/enhance.js:4`) and video export (`web/video.js:123`) also call this renderer.
- `web/app.js:1685` starts the serialized command operation, with queue assignment at `1713`; GUI/CLI/browser commands already share it. Precision controls belong in this command/schema/GUI contract, not a separate CLI encoder. `web/image-worker.js:5` owns codec concurrency, ownership transfer, startup handshake, timeout and same-kernel startup fallback.

## Other actions that must remain in the plan

**AI mask/depth analysis.** `ai-mask.js:5–46`, `depth.js:3–31` and `culling.js:2–15` deliberately resize to model/analysis surfaces. `ai-kernel.js:20–66`, `sky-kernel.js:13–86`, and `depth-kernel.js:18–41` create Float32 tensors from byte input and quantize probabilities/depth to u8. SDR model input is a legitimate explicit derived adapter; it must never become the float image source. Keep model normalization, coordinate mapping and provenance separate from working-color metadata. Increasing tensor storage precision does not retrain the model for HDR/wide gamut.

**Image-generating AI enhancement.** `enhance.js:4–18` bakes the *entire edited render* to bytes before inference and converts result to PNG. `enhance-kernel.js:57`, `:83–86`, `:105–117` takes byte-derived tensor input, clips denoiser prediction before encoding and returns Uint8ClampedArray. `app.js:969–987` stores this as a new PNG original with an empty recipe and source-edit provenance. A float renderer alone does not change this action. Preserve the current model's declared input transfer and dynamic-range assumptions. A future precise model adapter must return float output and retain/store a precise derivative; an SDR model may instead affect a declared bounded residual/region with high-range/color residuals preserved only after measurement. Do not invent that reconstruction's fidelity or call SDR inference sensor denoising.

**HDR and panorama.** `merge.js:13–25` uses the linear RAW special path for HDR only; other inputs use the ordinary byte decode. `merge-core.js:156–207` separately warps RAW Float32 values for HDR, while panorama warps encoded RGBA8 and only linearizes that result before float accumulation (`:490–506`). `mergeHDR` holds radiance Float32 (`:373`) but returns only tone-mapped bytes plus RGBE (`:423–424`); `merge-worker.js:6` transfers those, not the original float radiance. `merge.js:40–54` stores a tone-mapped PNG and optional RGBE blob. `app.js:1030` persists that pair, ordinary `source` decodes the PNG, and `export-hdr` (`:1628`) returns the unchanged RGBE before display edits. Retaining an editable scene-linear derivative needs the actual float buffer plus primaries/reference metadata, worker transfer and storage ownership; RGBE readback has already quantized shared exponents/mantissas. Keep existing `export-hdr` preservation semantics. Do not start baking display edits into this command as a side effect of precision work.

**Video.** `video.js:45–72` exposes HTMLVideoElement preview; `poster` uses ImageBitmap. Export `video.js:104–125` draws each decoded sample to default canvas, applies the same `render` and watermark, and returns canvas to Mediabunny/WebCodecs. A future float renderer can reuse the edits, but YUV/transfer/primaries/range decode and high-depth encoder transport still require video adapters. Current AVC/VP9 output cannot be called HDR just because still frames become float. Preserve trim/audio and validation for all tracks. Explicit output-color requests are currently rejected for video by the existing capability contract.

**Storage, sync and preservation.** `catalog.js:56` chunks only `file`, `thumbnail`, `radiance`; `:58` uses 8 MiB chunks without reducing original bytes. It preserves original precision even though rendering discards it. Do not persist every decoded float frame by default: cache it under source identity/decode version. Generated float derivatives need an owned media field/descriptor recognized by `packMedia`, hydration, orphan cleanup, delete/reference handling, sync manifests and restore. Catalog change alone is insufficient: local sidecars (`local.js:101`), XMP validation (`xmp.js:71–104`), versions, presets, clipboard and migration must preserve/validate the processing version and any new mask/patch encodings. `xmp.js:65` exports complete edit JSON, but unknown processing-version fields currently fall through edit-argument validation, so new fields do not automatically round-trip.

Original, original-with-settings, XMP and DNG are preservation paths, not render paths. `dng.js:229–247` retains existing DNG or invokes the explicitly calibrated linear RAW writer; `dng.js:182–190` quantizes normalized linear samples to 16-bit and rejects out-of-range scene samples. Its XYZ-to-linear-sRGB calibration must not remain unchanged if RAW output primaries are changed. External edit (`app.js:905–908`, `external.js:15`) delegates to normal TIFF export and can benefit from the precise TIFF path; native file transfer itself is lossless.

## Concrete migration sequence

1. **Specify and test the numerical contract.** Introduce an owned frame with width/height, Float32 straight RGBA (alpha [0,1]), explicit linear primaries/white point, decode provenance and resource disposal. Validate integer dimensions, complete sample count and finite components. Preserve negative RGB and values >1; alpha is not a color channel. Use premultiplied *temporary* samples for interpolation/compositing and return straight RGBA. Reuse the existing color matrix/transfer definitions. Use source/decode version for source caches and asset/edit revision/output dimensions for derived caches.
2. **Make one renderer consume the frame across all ordinary still edits.** Extract each current operator into numeric logic plus surface adapters; retain the stage sequence above in `render.js`. Port fill composition, red-eye, repair, depth blur, local mask adjustment, optics sampling, crop/resize, global tone/curve/mixer/spatial and watermark. Stage functions declare their working domains. Legacy compatibility may retain an explicit canvas resampler/rounding policy inside that shared stage while v2 uses float math. No full-frame conversion through ImageData between v2 stages. Final display conversion returns the canvas expected by the current UI; high-depth encoder receives the frame before that conversion.
3. **Connect genuine input and output in the same feature.** For the first shipped v2 route, preserve 16-bit TIFF source samples and validated matrix/TRC color transforms; add verified wide-gamut 16-bit LibRaw decode using its existing single kernel. Export true 16-bit tagged TIFF through the existing dynamic serializer; optionally PNG16 once independently read back. AVIF/JXL high-depth bindings are subsequent format additions. A source decoded through an 8-bit/native compatibility adapter stays accurately identified; a v2 render cannot retroactively claim source precision for it.
4. **Version activation and look compatibility.** Absence of processing version means current legacy behavior. Do not silently upgrade saved recipes, presets or named versions on reload. Offer an explicit version change and keep that state inside the shared command/recipe validation. New imports can default to v2 only after its full edit coverage and intended look are accepted. An old RGBA8 fill or u8 mask remains readable as a locally limited input; a whole-render byte fallback is reported as such. Keep one dispatcher and one scheduler for preview/export/thumbnail/video edits.
5. **Extend derivative-producing operations.** Store HDR Float32 before tone mapping; make panorama warp/blend float sources; add precise generated-fill payloads and measured enhancement/model adapters. Extend storage/sync and regenerate only caches. Keep the current tone-mapped PNG/RGBE and enhancement PNG behaviors as versioned legacy actions. Add video high-depth/color transport separately without diverging edit logic. Broader arbitrary ICC, HDR transfer/display and perceptual gamut mapping require their own explicit contracts.

An unbounded linear-sRGB working representation is a practical initial option because the tonal coefficients and existing linear-sRGB transform helper already match it: negative or >1 components can mathematically represent colors outside the sRGB display gamut. This is different from retaining *clipped* sRGB decode values. A linear ProPhoto/Rec.2020 working space is also viable, but every luminance coefficient, white-point adaptation and domain-sensitive operator must follow that choice. Do not rename sRGB samples as ProPhoto. LibRaw has different internal output matrices in the retained source archive (`src/tables/colorconst.cpp`); verify actual output selection, normalization, white point and saturated samples against those sources and independent expected colors before relying on it. The existing decoder is still a normalized 16-bit processed-RAW ceiling; full sensor dynamic-range preservation needs additional decoder work and must not be claimed from this migration.

## Verification that would establish the feature

Use small generated fixtures and the retained licensed RAW fixture; keep personal images out of tests. Existing tests are useful regressions, but their current 8-bit round trips do not prove the proposed path.

- Preserve two source values that map to the same byte; exercise local exposure, clone/heal, lens blur, optics, crop/resize, global exposure/curve/HSL/spatial and a watermark individually and in a combined recipe. Inspect the float stage/output and raw independently decoded 16-bit TIFF samples. Expect continuous math error/one output quantum, not the old 1/255 spacing.
- Include valid wide-gamut colors outside sRGB, negative working RGB, values >1 and semi/fully transparent edges. Export back into a target containing those colors and compare against independent matrix/CMS expectations. Include a negative-exposure highlight recovery case that fails if an early stage clamps to display white. Check TCA channels and alpha independently.
- Keep byte-exact baseline render snapshots for representative v1 recipes at source and fit sizes, including repeated masks, baked fill, repair, tone curve, grain and transparent geometry. A deliberate v2 look difference belongs in documentation and tests, not a loose tolerance that conceals it.
- Run actual GUI import/edit/reload/export and agent preview/export through the shared dispatcher; check identical recipe/version, original SHA-256, named-version/XMP/local-sidecar/sync round trips, and actual sample depth/ICC. Force worker startup failure to prove the same kernel works with retained typed-buffer ownership. Reject malformed frame/patch/profile/depth metadata visibly.
- Test asset/edit revision invalidation while decode/AI/render is pending. Current enhancement uses identity guards (`app.js:957–960`), and AI operations have similar guards (`:1260–1271`, `:1302–1308`); the future async renderer must preserve this contract. Do not assume the codec queue itself establishes selection ownership.
- Measure source-size and viewport-size time and peak memory. Float RGBA is 16 bytes/pixel before source copies, patches, warp outputs and spatial/blur scratch; a 24 MP frame alone is 384 MB. Preserve the no-arbitrary-size-ceiling rule with bounded concurrency, tiled operators/halos and visible allocation errors, rather than imposing a new file cap. Browser canvas results do not establish Windows/macOS/Linux native CMS/video behavior.

This audit executed source/document inspection and repository status checks only. It did not execute image quality tests, native GUI checks or benchmarks and does not claim those passed.
