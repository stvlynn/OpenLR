## Inspected path and API evidence

Further inspection used the matching Chromium 156.0.8078.80 source. [`HTMLVideoElement::CheckUsability`](https://github.com/chromium/chromium/blob/156.0.8078.80/third_party/blink/renderer/core/html/media/html_video_element.cc#L952-L957) returns invalid when no video frame is available. [`HasAvailableVideoFrame`](https://github.com/chromium/chromium/blob/156.0.8078.80/third_party/blink/renderer/platform/media/web_media_player_impl.cc#L1523-L1525) reads the first-frame flag; [compositor callback delivery](https://github.com/chromium/chromium/blob/156.0.8078.80/third_party/blink/renderer/platform/media/web_media_player_impl.cc#L2826-L2835) and [buffering readiness](https://github.com/chromium/chromium/blob/156.0.8078.80/third_party/blink/renderer/platform/media/web_media_player_impl.cc#L2166-L2189) use separate paths. An ordering race is a hypothesis, not a diagnosed cause of either recorded failure. A canvas substitution is not established recovery: [`drawImage(video)`](https://github.com/chromium/chromium/blob/156.0.8078.80/third_party/blink/renderer/modules/canvas/canvas2d/canvas_2d_recorder_context.cc#L2109-L2113) checks the same availability and can return without drawing.

A bounded new probe executed nine complete 48×32 ten-frame mixed-media workflows (three sequential, six across two concurrent independent Chrome processes). All succeeded with readyState 4 and four decoded frames at poster extraction, unchanged original bytes, a 24×16 still and a red sample of `[208,33,32,255]`. These observations did not reproduce the failure or justify a production retry. Ignored `.workspace/video-source-probe.mjs/.json/.log` retains evidence. A subsequent full-suite launcher `.workspace/video-bitmap-full-preload.mjs` adds passive rejection snapshots and preceding media-event history while preserving the actual bitmap promise; its run outcome must be recorded separately, and instrumentation can perturb timing.

`importBatch` calls `poster` for video files before storing the original or adding the photo record. `poster` awaits `openVideo`, awaits `createImageBitmap(media.video)` and closes the media in `finally`. `openVideo` registers its `loadeddata` listener before assigning the object URL; it also rejects media errors and zero dimensions/duration. There is no explicit close before the bitmap promise settles in this path. This source inspection does not prove the browser always retains a usable decoded frame.

Context7 `/mdn/content` documents [readyState](https://github.com/mdn/content/blob/main/files/en-us/web/api/htmlmediaelement/readystate/index.md): `HAVE_CURRENT_DATA` indicates data for the current position, while `HAVE_ENOUGH_DATA` additionally supports continued playback. [createImageBitmap](https://github.com/mdn/content/blob/main/files/en-us/web/api/window/createimagebitmap/index.md) accepts a video source. These contracts do not retrospectively establish the state of the failed remote element. No additional delay, automatic decode retry, timeout increase or alternative extraction algorithm was adopted from this single failure.
